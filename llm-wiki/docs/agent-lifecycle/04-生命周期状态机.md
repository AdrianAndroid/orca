# 第 4 章 · 生命周期状态机:从启动到清理

> 一个 agent 状态行的完整一生:启动注册 → 事件流与租约 → 退出判定 → 清理。
> 退出判定是全章重点:**四条独立通道,每条都要求正面证据**。引用为仓库相对路径。

---

## 4.0 状态机总图

```
        launch(env 注入 hook 端点)
            │
            ▼
     ┌── 未注册 ──┐  首个 hook POST(带 launchToken)
     │            ▼
     │      ┌──────────┐   PreToolUse 等    ┌──────────┐
     │      │ working  │ ◄────────────────► │ blocked/ │  权限/提问事件
     │      └────┬─────┘   新证据续租        │ waiting  │
     │           │ 30min 无证据              └──────────┘
     │           ▼
     │      ┌──────────┐   有 live PTY → unverifiable 圆点
     │      │  stale   │   无 PTY      → idle 圆点
     │      └────┬─────┘   (renderer 派生,行本身不动)
     │           │
     │           ▼ 退出判定四通道(§4.3),均需正面证据
     │      ┌──────────┐
     └─────►│ exited / │  清理:clearPaneCacheState + fence
            │ retired  │  (resume 身份保留)
            └──────────┘
```

## 4.1 启动与注册

### 启动器与 hook 注入

`src/main/agent-launch/agent-launch-executor.ts` 决定 launch mode、建 workspace、投递 prompt;PTY 环境变量由 `agentHookRuntimeDeps.buildAgentHookPtyEnv` 注入(`agent-hook-runtime-deps.ts:52-54`,仅当 `isAgentStatusHooksEnabled`)——agent 进程一出生就带着 hook 端点地址和令牌。

### 注册 = 首个 hook POST

没有显式的"注册 RPC":**agent 的第一个 hook POST 即注册**,携带 paneKey、launchToken、进程身份(pid + startTime + platform)。两个门卫:

- **launchToken fence**(`listener-state.ts:81-82`):"a rewritten shared-server post needs the bound pane's live token to pass its fence"——pane 只认当前 launch 的令牌,上一个 launch 的僵尸进程发的 hook 直接拒收;
- **进程身份登记**:`agentPresence.process`,后续所有退出判定都拿它当锚。

### 会话所有权:不发终止 hook 的退出怎么办

Claude 的 `/clear`、relaunch、resume 会换掉 `session_id` 而不发 SessionEnd。兜底是 `claudeSessionOwnerByPaneKey`(`listener-state.ts:58-61`):

> "A different id means the conversation was replaced (/clear, relaunch, resume), so claims the old session owned are void even when no SessionStart arrives — **the backstop for the exits that emit no terminating hook**."

session 换人即旧 claims 作废——不需要"退出事件",**身份变更本身就是死亡证明**。

---

## 4.2 事件流:无心跳的租约制

系统没有周期心跳(第 3 章 §3.4):hook 事件即证据,30 分钟无证据即 stale。`blocked`/`waiting` 由 provider 事件直接给出(权限 prompt、AskUserQuestion、Notification),规则分散在 `server-claude-status-rules.ts`、`server-ingest-normalization.ts` 与 `src/shared/agent-hook-listener/providers/`。

**idle 不是摄取来的状态**——它是 renderer 的派生态(`agent-row-decay-state.ts:26-31`):stale 且无 live PTY → `idle`;stale 但有 live PTY → `unverifiable`。store 里的行不随时间变质,**衰减只发生在呈现层**。这让"30 分钟"成为纯 UI 策略,而非状态语义。

## 4.3 退出判定:四条通道,都要正面证据

### 通道 1:终止 hook(agent 自报)

SessionEnd/Stop 携带进程身份 → `reconcileEndedProcessForPaneKeys`(`server-cleanup.ts:126`)。但有个硬条件,测试名即规则:`server-agent-presence.test.ts:122` —— **"never ends a pane from a SessionEnd without a process identity"**。没有进程身份的终止 hook 说明不了死的是谁,不足为证。

### 通道 2:主动探针(他者质疑)

`checkAgentPresenceAfterHook`(`server-agent-presence.ts:18-36`),头注释一句话说清触发条件:

> "A live hook proves its own process alive; **only another process's hook casts doubt on the owner**."

自己的 hook 证明自己活着,永远不会触发自查;只有**另一个进程**从同一 pane 上报,才质疑现任 owner 是否还活着,此时探 `/proc`。并发探针用 WeakMap 去重(:10-16)——同一行在途探针只有一个。

探针回来之后还有一道复核(:85-92):token、generation、行身份、presence 全部重新校验,任何一项变了都返回 `unverifiable` 放弃判死——**防"迟到探针杀死重启的 agent"**(测试 `server-agent-presence.test.ts:280`:"does not apply a delayed process exit to a relaunched agent")。

```ts
.then((verdict) => {
  if (
    !this.statusHooksEnabled ||
    this.token !== token ||
    this.statusHookGeneration !== statusHookGeneration ||
    this.state.lastStatusByPaneKey.get(resolved) !== row ||
    row.agentPresence !== presence
  ) {
    return 'unverifiable' as const
  }
```

五个条件对应五种"世界在 await 期间变了"的场景——这是 worktree 系列"await 后重读世界"模式在 agent 域的同款(见 [worktree 系列 §6.1 模式 2](../worktree-orchestration/06-设计模式与原则.md))。

### 通道 3:退出证据保留(跨键共享)

证实的退出存进 `agentExitedAtByPaneKey`(`server-state.ts:79`),`AgentExitEvidence` 的头注释(`server/agent-exit-evidence.ts:9`):

> "A proven agent exit, shared by every key the pane was addressed by when it ended."

证据**活得比行久**("outlives the row the exit reconciles"):pane 重启、键改名之后,旧的退出证据仍然有效,`checkAgentPresenceSince`(`server-agent-presence.ts:50`)回答"某时刻之后有没有证实的退出"——relay 重连对账就靠它(第 5 章)。

### 通道 4:冷启动扫尾(替身退出)

Orca 关闭期间终端死了,没人走 PTY-exit teardown——恢复的行会永远声称有工作。`retireRestoredStatusesWithDeadTerminals`(`restored-status-dead-terminal-sweep.ts:31-70`):

> "A terminal that dies while Orca is down never reaches the PTY-exit teardown, so its restored row would claim work forever. **Stand in for that exit**: retire restored rows whose local PTY the provider proves absent, **through the same path an observed exit takes**."

两个细节:探针抛异常 → `null` → 不算证据(:42,"a probe that throws is unverifiable, never evidence the terminal died");扫尾走**与真实退出相同的路径**,不发明第二条退休通道。退役时 `preserveResumeIdentity: true`(:67-70)——对话比终端活得久,行可以死,resume 能力必须留下。

## 4.4 清理:什么能清,什么不能动

### state claim:teardown 的准入清单

`clearPaneCacheState`(`listener-state.ts:201`)清 pane 的全部缓存——但谁来决定"能不能清"?`paneHasStateClaims`(:231-250),头注释即设计理由:

> "Does this pane still hold anything that can ASSERT a state — a stored row, or a Claude latch that `resolveClaudePaneStatus` would re-gate `working` from on the pane's next event? ... the two must be edited together, and **keeping them three lines apart in one file is what makes that obvious**."

"能断言状态的"才算 claim:存储的行、subagent roster、lead state、后台任务 claim 集、session owner。而 prompt/tool/transcript 缓存不算——"they render a row, they never create one"。判断函数与清除函数刻意放在同一文件隔三行,**物理 proximity 强制同步编辑**。

### 清理入口

- pane 级:`clearPaneCacheState`;
- worktree 删除:`dropStatusEntriesForRemovedWorktree`;
- authority 退休 fence:"retirement fences a pane and every alias of it"(`server-authority-fences.ts:11-12`);
- 全量换代:`statusHookGeneration += 1`(第 5 章)。

## 4.5 关键测试(威胁模型即测试名)

`src/main/agent-hooks/server-agent-presence.test.ts` 是学习退出判定攻击面的最好材料:

| 测试 | 防的是什么 |
|---|---|
| "never ends a pane from a SessionEnd without a process identity"(:122) | 无身份终止 hook 误杀 |
| "accepts a remote exit and never probes that remote PID locally"(:298) | 本机探远端 PID(可能撞上本地无关进程) |
| "probes the owner only when another process reports, never on its own hooks or retries"(:329) | 自查风暴 |
| "does not apply a delayed process exit to a relaunched agent"(:280) | 迟到探针杀新 agent |
