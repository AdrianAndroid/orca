# 第 5 章 · 并发护栏与跨主机边界

> 上一章的状态机是"正常路径";本章讲让它在并发与多主机下仍然正确的护栏。
> 两类问题:① 异步世界里"await 之后世界变了";② SSH 世界里"远端状态谁说了算"。引用为仓库相对路径。

---

## 5.1 护栏总表

| 护栏 | 机制 | 防的是什么 | 出处 |
|---|---|---|---|
| **generation fence** | `statusHookGeneration += 1` 使在途异步工作失效 | 配置开关切换后旧异步写状态 | `server-status-hook-lifecycle.ts:11` |
| **launchToken fence** | pane 只认当前 launch 的令牌 | 僵尸进程冒名上报 | `listener-state.ts:81-82` |
| **retired-pane fence** | 退休的 pane 及其全部 alias 一并围栏 | 已退休 pane 的迟到事件复活 | `server-authority-fences.ts:11-12` |
| **探针后五重复核** | token/generation/行身份/presence 重校验 | 迟到探针杀死重启的 agent | `server-agent-presence.ts:85-92` |
| **探针 WeakMap 去重** | 同一行在途探针只有一个 | 探针风暴 | `server-agent-presence.ts:10-16` |
| **session owner 换代** | session_id 变更即旧 claims 作废 | 无终止 hook 的退出 | `listener-state.ts:58-61` |
| **owner-challenge 计数** | 只有他者进程上报才触发探针 | 自查风暴 | `server-agent-presence.ts:18-36` |
| **exit evidence 跨键共享** | 退出证据活得比行久 | pane 改名后证据丢失 | `server/agent-exit-evidence.ts:9` |

共同点:**所有护栏的失败方向都是 unverifiable / 不动作**,没有任何一条在证据不足时偏向"死了"或"清了"——与第 3 章的三态语义互为表里。

## 5.2 三类 fence 详解

### generation fence:一键作废在途工作

```ts
this.statusHookGeneration += 1   // server-status-hook-lifecycle.ts:11
```

hook 开关切换时 generation 自增。所有在途异步操作(探针、持久化)启动时记下当时的 generation,回来先比对——不等即放弃。这是 worktree 系列"世代号防伪"模式(`local-worktree-scan-generation.ts`)的同款:**单调递增的代数比任何锁都便宜地解决了"旧操作在新世界写状态"**。

### launchToken fence:绑定到一次 launch

`lastLaunchTokenByPaneKey`(`listener-state.ts:81-82`)记录 pane 最近一次 launch 的令牌。rewrite 过的 shared-server POST 必须持该 pane 的 live token 才能过栏——上一个 launch 的进程哪怕还活着、还在发 hook,也写不进新 launch 的行。

### retired-pane fence:退休即永久

> "Why: retirement fences a pane and every alias of it, then deletes those aliases."(`server-authority-fences.ts:11-12`)

注意 **every alias**:pane 在生命周期中可能有多个键(改名、迁移),退休一个就要围栏全部——否则迟到事件从 alias 侧门溜进来,退休形同虚设。

## 5.3 跨主机边界:execution host owns status

### 每台主机一个权威

desktop、`orca serve`、orcad 各自跑自己的 `AgentHookServer` + `HookListenerState`,"each get their own, never shared"(`listener-state.ts:32`)。远端 agent 的状态:

1. 远端 hook server 归一化(与本地同一份 shared 代码);
2. relay 以 `agent.hook` 上行,wire `connectionId` 恒 null(第 2 章 §2.2);
3. 本地 `ingestRemote` **在信任边界再归一化**,盖上本地 connectionId 入库。

### 探针边界:本机绝不探远端 PID

`server-agent-presence.ts:71-74`:

```ts
if (row.connectionId !== null) {
  return Promise.resolve('unverifiable')
}
```

行带着 connectionId = 这进程在远端。本机探它的 PID 可能撞上本地完全无关的进程(PID 空间各主机独立),所以远端行**永远 unverifiable,永不本地探**。测试 :298 钉死:"accepts a remote exit and never probes that remote PID locally"——远端退出由远端主机证实后经 relay 下达。

### renderer 侧的同构规则

同样的边界在 renderer 复现(`use-terminal-watcher-effects.ts:211-212`,STA-4658):

> "Why: **the execution host owns terminal creation, and a host that has not answered is not a host with no terminals** — seeding into that gap duplicates its tabs on every launch."

主机没回答 ≠ 主机没终端。往这个认知缺口里"播种"本地假设,每次启动都会复制一遍远端 tab。

parked PTY watcher 同款(`terminal-parked-pty-watcher.ts:73`):

> "A negative code is a synthetic loss sentinel, **not a death certificate**."

### wire 层的失联表达:unverifiableTerminalCount

relay 一断,该主机全部 PTY 记录同时消失——如果只看 live 计数,行会读作"什么终端都没有"。所以 wire 上有专门字段(`src/main/runtime/runtime-worktree-ps-unverifiable-terminals.ts:5-9`):

> "Counts each terminal that was not counted live but whose host only lost contact. A relay drop disconnects every one of the host's PTY records at once, so without this the row read as no terminals at all."

字段定义在 `src/shared/runtime-worktree-contracts.ts:101`,**optional**——这是 wire 兼容守则的落码:新字段 optional,旧客户端不认识就跳过;旧主机没这字段时新客户端读作 unverifiable(`worktree-ps-terminal-verdict.ts:15-19`),`hostScope` 缺省(:183)同样按 unverifiable 读。**两个方向的版本混布都退化成"不知道",而不是"没有"**。

### 断连期间的镜像与重连对账

- 断连时 renderer 保留镜像,但标记 unverifiable(#7718 的教训:`remote-runtime-pty-transport.ts:1803`——stale handle 应该 retire mirror 而不是红屏报错);
- 重连后:relay 重放缓存行并重新盖章(时钟规则见第 3 章 §3.4);`checkAgentPresenceSince`(`server-agent-presence.ts:50`)回答"断连期间有没有证实的退出";中断推断走 mux RPC(`src/main/ssh/ssh-agent-hook-interrupt-reconciliation.ts:6-19`)。

### orcad 的自主退出

远端守护不会永远活着:`orcad-entry.ts:184` `beginOrcadIdleExit` 让它空闲时自行退出(e2e:`tests/e2e/ssh-orcad-idle-exit.spec.ts`)。orcad 退出不等于 agent 退出——agent 进程归 SSH 主机管,不归 orcad 管。这再次回到同一条规则:**orcad 失联后,远端 agent 状态是 unverifiable,直到重连对账**。

## 5.4 模式对照(与 worktree 系列的呼应)

| 本系统 | worktree 编排 | 模式 |
|---|---|---|
| statusHookGeneration | scan generation | 世代号防伪 |
| 探针后五重复核 | reservePreparation 三次重选 | await 后重读世界 |
| 探针失败 → unverifiable | home 探查失败 → unverifiable | 空是危险值 |
| 探针 WeakMap 去重 | claim 单同步回合 | 同步性代替锁 |
| launchToken/retired fence | instanceId 防 ABA | 身份轮换防错配 |

两个子系统在不同的域里收敛到同一套并发语言——这不是巧合,是仓库级的设计文化(见 [worktree 系列第 6 章](../worktree-orchestration/06-设计模式与原则.md))。
