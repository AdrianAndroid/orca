# 第 1 章 · 概览与架构

> Orca agent 生命周期子系统总览:谁在记录 agent 的状态、状态长什么样、谁能读它。
> 核心命题一句话:**执行主机在唯一的 store 里拥有 agent 状态,所有读者只保留呈现策略**。
> 本系列共 6 章,本章是地图。引用为仓库相对路径。

---

## 1.1 系统定位

Orca 同时管理几十个 agent(Claude、Codex、Grok、Muse、OpenCode……),每个 agent 可能跑在本地 PTY、SSH 远端、或没有终端的 structured session 里。这个子系统回答四个问题:

| 问题 | 答案 | 章节 |
|---|---|---|
| agent 现在在干嘛? | 唯一 store 里的一行状态(`working/blocked/waiting/done`) | [第 3 章](./03-状态词表与三态语义.md) |
| 它还活着吗? | 进程三态 `live / unverifiable / exited`——只有正面证据才算 `exited` | [第 3 章](./03-状态词表与三态语义.md) |
| 状态从哪来? | hook POST / relay 转发 / OSC 9999 / structured 投影,四条路汇入同一 store | [第 2 章](./02-hook摄取管线.md) |
| 谁在看? | sidebar、`worktree ps`、mobile、dashboard——同一 store,各自呈现 | [第 6 章](./06-读者呈现与演进史.md) |

子系统的物理中心是 `AgentHookServer`:一个跑在每个执行主机上的 loopback HTTP 服务器 + 内存状态库。它由 `src/main/agent-hooks/server/` 下 **26 个 mixin 层**叠成——文件数量再次说明这个领域踩过大量坑,几乎每层都对应一类事故(见 [第 6 章](./06-读者呈现与演进史.md) 的演进史)。

## 1.2 术语表

| 术语 | 含义 |
|---|---|
| **hook** | agent CLI 在生命周期事件(PreToolUse、Notification、Stop、SessionEnd……)时向 Orca 发的 HTTP POST |
| **paneKey** | 状态行的作用域键:一个终端 pane 一行 |
| **hook server** | `AgentHookServer`,loopback HTTP 监听 + 状态 store 的合体,每执行主机一个 |
| **legacy 行 / canonical store** | 双通道:`lastStatusByPaneKey`(hook 原始行)与 `AgentStatusStore`(结构化行),读取处合并 |
| **authority / replica** | store 的两种模式:执行主机是 authority,别处(如 relay 对端)是 replica |
| **launchToken** | 启动时分发的令牌,后续 hook 必须持证进场——防止旧进程冒名 |
| **AgentProcessVerdict** | 进程三态词表:`live / unverifiable / exited`(`src/shared/agent-process-presence.ts:21`) |
| **OSC 9999** | PTY 字节流里的带内状态序列,main 的 PTY 解析是它的唯一生产者 |
| **structured session** | 无 PTY 无 hook 的 native chat,由 host 直接投影状态行进 store |
| **spool** | hook 落盘缓冲(5MB/1024 文件/7 天),启动时重放 |
| **stale** | 30 分钟无新证据的状态行(`AGENT_STATUS_STALE_AFTER_MS`) |
| **state claim** | pane 缓存里"还代表活着的工作"的条目集合,决定 teardown 能不能清 |

## 1.3 单一权威 store:双通道模型

状态存储是"**一个逻辑 store,两条写入通道**":

```
                 ┌────────────────────────────────────────┐
                 │           AgentHookServer              │
                 │  ┌──────────────────────────────────┐  │
   hook POST ───►│  │ legacy 行:lastStatusByPaneKey    │  │──┐
   relay 转发 ──►│  │ (只读兼容视图,写入走隔离适配器) │  │  │
   OSC 9999 ────►│  ├──────────────────────────────────┤  │  │ combinedStatusEntries()
   structured ──►│  │ canonical:AgentStatusStore       │  │  │ (server-listeners.ts:54)
   探针回写 ────►│  │ (authority 模式,epoch+revision) │  │  │
                 │  └──────────────────────────────────┘  │  │
                 └────────────────────────────────────────┘  │
                                ▼                             ▼
                     sidebar / worktree ps / mobile / dashboard
```

- **legacy 通道**:`HookListenerState.lastStatusByPaneKey`,注释明确定性——"Read-only compatibility view. All writes pass through the isolated legacy adapter."(`src/shared/agent-hook-listener/listener-state.ts:38-39`)。
- **canonical 通道**:`AgentStatusStore`(`src/shared/agent-status-store.ts:43`),模式 `'authority' | 'replica'`,带 epoch + revision 的 mutation/snapshot/transport-envelope 复制协议(`applyMutation` :122、`applySnapshot` :142、`applyTransportEnvelope` :172)。server 侧权威实例在 `src/main/agent-hooks/server/server-state.ts:70-76`,epoch 用 `randomUUID()`——**每次进程重启换 epoch,replica 据此识别 authority 换代**。
- **合并读取**:`combinedStatusEntries()`(`server-listeners.ts:54-57`)把两条通道合成统一视图给订阅者。

**为什么不能共享一个全局 store**:`HookListenerState` 的头注释直说——"Per-listener-instance caches needing per-PTY teardown; Orca's main process and the relay each get their own, never shared"(`listener-state.ts:32`)。每台执行主机自己的 store 是自己的权威;远端状态经 relay 上行后由本地 `ingestRemote` 盖章入库(见 [第 5 章](./05-并发护栏与跨主机边界.md))。

## 1.4 26 层 mixin:一个类的考古剖面

`AgentHookServer` 不是一个大文件,而是 26 个单职责 mixin 的层叠(`src/main/agent-hooks/server.ts:29-31` 只有三行):

```ts
export class AgentHookServer extends AgentHookServerAgentPresence {}
export const agentHookServer = new AgentHookServer()
```

继承链自顶向下(每层一个文件,`src/main/agent-hooks/server/`):

| 层 | 职责 |
|---|---|
| `server-agent-presence.ts` | 进程存在性探针(第 4 章) |
| `server-lifecycle.ts` | HTTP loopback listener(第 2 章) |
| `server-status-hook-lifecycle.ts` | hook 生命周期 + 生成号 fence |
| `server-runtime-env.ts` / `server-ingest-remote.ts` / `server-ingest-structured*.ts` / `server-ingest-terminal.ts` / `server-ingest-normalization.ts` | 五条摄取通道 |
| `server-tmux-status.ts` / `server-opencode-binder.ts` | provider 特化 |
| `server-persistence.ts` / `server-hydration.ts` | 落盘与冷启动水合 |
| `server-tab-cleanup.ts` / `server-cleanup.ts` | teardown |
| `server-authority-{fences,aliases,evidence}.ts` | 权威防护(第 5 章) |
| `server-status-{retries,update,application,disposition,inference}.ts` | 状态应用管线 |
| `server-row-ownership.ts` / `server-listeners.ts` / `server-state.ts` | 行所有权、订阅、基类 |

文件头注释给出分层动机:"keeps listener internals in shared/ so the relay can host the same pipeline without Electron"(`server.ts:1`)——**relay(SSH 远端)复用同一条摄取管线,只是宿主进程不同**。

## 1.6 这个子系统最重要的设计宣言

在深入之前,先立住全系列反复引用的两条:

1. **"only positive proof earns `exited`"**(`src/main/daemon/daemon-liveness-report.ts:2-7`)——`exited` 必须来自正面证据(可读的 `/proc` 消失、终止 hook、探针确认);任何怀疑、超时、异常都只能到 `unverifiable` 为止。第 3 章整章展开。
2. **"Silence is not evidence"**(`src/renderer/src/lib/agent-row-decay-state.ts:14-22`)——沉默只说明"报告流安静了",不说明 agent 完了。PT​Y 还在 = `unverifiable`;PTY 没了 = `idle`;两者都不宣称 agent 结束。

> 注:这两处注释都引用 `docs/reference/ssh-execution-boundary.md`,但该文档在当前 checkout 不存在——代码注释即一手来源,本系列按代码引用编目。
