# 第 6 章 · 读者呈现、演进史与阅读路径

> 前五章讲状态怎么来、怎么判;本章讲状态怎么被消费,以及这个子系统从事故里学到了什么。
> 读者规则一句话:**四类读者订阅同一 store,只保留呈现策略**。引用为仓库相对路径。

## 6.1 四类读者总览

| 读者 | 传输 | 关键路径 | 呈现策略要点 |
|---|---|---|---|
| **sidebar** | IPC `agentStatus:set/clear` → zustand | `src/main/startup/main-window-agent-status.ts:14` | 聚合排序、衰减、共享圆点词表 |
| **dashboard** | 同一 IPC(popout 直发) | `main-window-agent-status.ts:86,94` | 复用 sidebar 的词表与映射 |
| **`worktree ps` CLI** | JSON-RPC `worktree.ps` 一次性响应 | `src/main/runtime/rpc/methods/worktree-catalog-methods.ts:19` | `live/unverifiable/none` 文案投影 |
| **mobile** | `worktree.ps` 轮询 + snapshotId 条件请求 | `mobile/src/worktree/worktree-catalog-snapshot-client.ts:7-26` | 镜像复刻桌面词表,parity test 对齐 |

### sidebar:聚合排序即优先级

`worktree-card-agent-summary.ts:13-28` 的 SUMMARY_STATE_ORDER,每档都有 Why 注释:

```ts
'blocked',
// Why: a failed main agent outranks live work; a pending question still comes first.
'failed',
'working',
'monitoring',
'unconfirmed',
// Why: a user's Stop is not news, but it is not a finish either.
'interrupted',
```

排序即产品判断:**要人处理的在前,失败压过正在进行,用户主动停的不算新闻也不算完成**。

### 单写者纪律:一个 paneKey 一个写者

`main-window-agent-status.ts:38-40`:

> "Why: the renderer still derives structured rows from its own feed subscription; forwarding these too would give **one pane key two writers** until that bridge is retired."

过渡期也不许两个写者——宁可少转发,不让一个 pane 的状态有两个来源。

### 共享词表防漂移

`agent-row-dot-state.ts:11-42`:

> "One copy so the sidebar card, the dashboard row and the notes send menu **cannot drift on a new member**."

展示映射只有一份,新增状态成员时三个 UI 不可能各改各的。跨进程的一致性锚点同理(`structured-agent-session-agent-status.ts:26-29`):

> "Shared across the process boundary so `worktree ps`, mobile and the sidebar **cannot disagree about one session**."

### mobile:镜像复刻 + 失败≠空

mobile 不能 import 桌面运行时值(vitest transform 限制),所以**本地复刻**词表与 30 分钟窗口(`mobile/src/worktree/agent-row-display.ts:4-20`),用 parity test 强制对齐。这是"单一来源"原则的务实变体:物理上无法共享时,用测试钉住语义等价。

拉取失败的处理(STA-3123,`worktree-catalog-snapshot-client.ts:20-24`):

> "Why (STA-3123): a failed worktree.ps must stay distinguishable from an empty catalog — collapsing both to 'no rows' made **unreachable remote-server catalogs render as a healthy host with 0 worktrees**."

又是同一条原则:失败是"不知道",不是"没有"。

### CLI:词表上就不给 `exited`

`worktree ps` 的终端判定是 `live / unverifiable / none`(`src/cli/worktree-ps-terminal-verdict.ts:8`)——CLI 拿不到进程级证据,词表里直接没有 `exited` 这个词(第 3 章 §3.3)。

## 6.3 设计模式汇总(本系列提炼)

| # | 模式 | 体现 |
|---|---|---|
| 1 | **事件驱动 + 租约**,无心跳 | hook 即证据,30min 窗口,重复证据续租不变异行 |
| 2 | **fail-open 摄取** | 畸形 payload 回 204;hook 坏了不卡 agent |
| 3 | **只有正面证据能判死** | 三态词表无同义词;CLI 词表连 `exited` 都没有 |
| 4 | **空是危险值** | 空句柄表/空快照/失败响应全部读作"不知道" |
| 5 | **双通道单 store,读取处合并** | legacy 行 + canonical store,`combinedStatusEntries()` |
| 6 | **衰减在呈现层** | store 行不变质;idle/unverifiable 是 renderer 派生 |
| 7 | **时钟在用者一侧** | 镜像行带 replica 接收时刻,衰减永远在读者钟上量 |
| 8 | **单写者 per paneKey** | OSC 解析是 PTY agent 唯一生产者;过渡期也不许双写 |
| 9 | **fence 三件套** | generation / launchToken / retired-pane,失败方向全是"不动作" |
| 10 | **proximity 强制同步编辑** | `paneHasStateClaims` 与 `clearPaneCacheState` 隔三行同文件 |
