# 第 1 章 · 概览与架构

> Orca 终端/PTY 子系统总览:为什么终端住在一个独立 daemon 进程里、各层如何分工、app 重启/更新后终端凭什么还活着。
> 核心命题一句话:**终端是用户的财产,Orca 进程只是它的租客——app 可以死,终端不能死**。引用为仓库相对路径。

---

## 1.1 系统定位

Orca 的每个 pane 后面是一个真实 PTY,里面跑着用户的 shell、agent CLI、构建任务。这些进程的寿命经常超过 Orca 本身:用户关 app 吃饭去了,编译还得继续;app 自动更新,`npm run dev` 不能被杀。这个子系统回答四个问题:

| 问题 | 答案 | 章节 |
|---|---|---|
| 终端凭什么活得比 app 久? | PTY 由独立 daemon 进程持有,app 退出时**断连不杀** | [第 2 章](./02-daemon生命周期.md) |
| 进程怎么管(尤其 Windows)? | node-pty + 1466 行 Orca 补丁:job object、breakaway 策略 | [第 3 章](./03-pty层.md) |
| shell 怎么变成"可观测"的? | 内容寻址的 shell wrapper 注入 OSC 133/777 钩子 | [第 4 章](./04-shell-wrapper体系.md) |
| 关掉的终端怎么复活? | daemon 增量 history + workspace-session 快照,两套机制 | [第 5 章](./05-scrollback与恢复.md) |

## 1.2 术语表

| 术语 | 含义 |
|---|---|
| **terminal daemon** | 独立 Node 进程,持有全部 PTY;与 app 通过 socket 通信 |
| **TerminalHost** | daemon 内的 session 注册表(`src/main/daemon/terminal-host.ts:41`) |
| **Session** | daemon 内一个 PTY 会话:输出管线、shell-ready 屏障、终止控制 |
| **HeadlessEmulator** | daemon 内的 `@xterm/headless` 屏幕模型,快照/replay 的序列化源 |
| **endpoint** | daemon 的 socket 端点(Unix socket / Windows named pipe),有严格所有权协议 |
| **adapter / router** | 主进程侧的 daemon 客户端封装;router 在**多代 daemon** 间路由 |
| **checkpoint / output.log** | daemon history 的两件套:周期性全量快照 + 增量输出日志 |
| **cold restore** | app 重启后从 checkpoint+log 重建终端画面的流程 |
| **shell wrapper** | Orca 生成的 shell 启动文件树,注入 ready marker 与 OSC 133 |
| **OSC 133 / 777** | 命令生命周期标记(A/B/C/D)/ shell-ready 标记 |
| **job object** | Windows 内核进程组;Orca 用它替代不可靠的 pid 走查 |
| **breakaway** | 子进程逃出 job 的 Windows 机制;MSYS 全家桶会滥用它 |
| **daemon-host relocation** | Windows 上把 daemon 进程镜像搬到 `%LOCALAPPDATA%` 躲更新 |
| **TCC attribution** | macOS 隐私授权的归属问题;daemon 必须以 app 身份启动 |

## 1.3 进程拓扑

```
┌───────────────────────── Orca app (Electron) ─────────────────────────┐
│ renderer                    主进程                                     │
│ @xterm/xterm               OrcaRuntimeTerminal*(mixin 层叠)            │
│  + serialize/webgl  ──►    DaemonPtyRouter ──► DaemonPtyAdapter       │
│  /search addons            (多代路由 :25)      (15 层 mixin)           │
│                                    │            │                     │
│                                    │      DaemonClient(:37)           │
│                                    │      control+stream 双 socket    │
└────────────────────────────────────┼────────────┼─────────────────────┘
                                     │ NDJSON over Unix socket / named pipe
┌────────────────────────────────────▼────────────▼─────────────────────┐
│ terminal daemon(独立 Node 进程,app 死了它活着)                      │
│  DaemonServer ──► TerminalHost(session 注册表/tombstone/认领)       │
│                ──► Session ──► SubprocessHandle ──► node-pty          │
│                ──► HeadlessEmulator(屏幕模型,快照来源)              │
│                ──► terminal-history/*(checkpoint+log 落盘)            │
└────────────────────────────────────────────────────────────────────────┘
```

- **协议**:`PROTOCOL_VERSION = 48`(`src/main/daemon/daemon-protocol-version.ts:8`),头注释一句话定规矩——"Why: daemons survive app updates, so wire behavior must be version-gated"(:1)。**daemon 活得比 app 版本久,所以线协议按版本门控**;v48 的注释本身就是一部微缩版本史(:2-7)。
- **多代共存**:app 更新后旧 daemon 仍在跑(里面还有活 session),新 app 启动新 daemon——`DaemonPtyRouter` 持有 current + legacy adapters,按 session 归属路由(`daemon-pty-router.ts:25-28`);history 跨代移交有协议版本门槛(`daemon-history-handoff.ts:4-14`,v30)。
- **无 Electron 复用**:`src/main/orcad/`(SSH 远端守护)复用同一 daemon/PTY 栈,不依赖 Electron。

## 1.4 为什么 daemon 化:四条决定性注释

### ① 断连不杀(`src/main/daemon/daemon-provider-state.ts:115-120`)

```ts
// Disconnect without killing: the daemon survives app quit so sessions stay warm
// for reattach. Leave history sessions marked "unclean" so a daemon crash while
// Orca is closed stays recoverable.
export async function disconnectDaemon(): Promise<void> {
```

app 退出路径只断开 socket,**不动 PTY**。"unclean" 标记则让"app 关着的时候 daemon 崩了"这个组合也能恢复(第 5 章)。

### ② socket 复用即存活证明(`daemon-launch-paths.ts:58`)

> "Why: a socket that accepts a connection proves a daemon survived a previous app session and can be reused."

启动时不急着 fork 新 daemon:先探测旧 socket,能连上就直接收养上一代 daemon(连同它所有的活终端)。

### ③ 60 秒 fail-open 硬上限(`src/main/startup/first-window-startup-services.ts:25`)

```ts
// waits for the daemon attempt itself and only fail-opens at a hard cap that
// exists solely as a deadlock backstop.
export const LOCAL_PTY_STARTUP_FAIL_OPEN_TIMEOUT_MS = 60_000
```

daemon 起不来(被杀软拦、磁盘坏)时,app 不能永远没有终端——60 秒后退化到主进程内本地 PTY provider。**daemon 是优化不是前提**,这个兜底是死锁保险,不是正常路径。

### ④ Windows/macOS 上"从哪 fork"本身就是问题

- Windows:NSIS 更新删旧安装目录并强杀其下所有进程镜像 → daemon 必须搬到 `%LOCALAPPDATA%`(`daemon-host-relocation.ts:31-41`,第 7 章);
- macOS:从 app fork 的 daemon 在更新后失去 TCC 隐私授权 → 用 launchd 从签名副本启动(`docs/reference/macos-daemon-tcc-attribution.md`,第 7 章)。

## 1.5 模块全景

| 层 | 位置 | 职责 |
|---|---|---|
| Renderer | `src/renderer/src/lib/pane-manager/`、`components/terminal-pane/` | xterm 视图、layout replay、scrollback 捕获 |
| 主进程 runtime | `src/main/runtime/terminal/`(launch/lifecycle/output/adoption/recovery 子目录) | 编排:create、输出摄取、title 跟踪、孤儿收养 |
| Provider 契约 | `src/main/providers/pty-provider-contract.ts:46`(`PtySpawnOptions`) | 本地/daemon/SSH provider 统一接口 |
| Daemon 客户端 | `src/main/daemon/daemon-pty-*.ts`(约 15 层)、`client.ts`、`daemon-pty-router.ts` | socket、重连、respawn、checkpoint、多代路由 |
| Daemon 进程 | `src/main/daemon/{daemon-entry,daemon-main,daemon-server,terminal-host,session}.ts` | 持有全部 PTY,NDJSON 服务 |
| PTY 原生层 | `node-pty@1.1.0` + `config/patches/node-pty@1.1.0.patch`(1466 行) | spawn、job object、进程上限 |
| Headless | `src/main/daemon/headless-emulator.ts` | 屏幕模型、序列化 |
| Shell wrapper | `src/main/shell-wrapper-*.ts`、`zsh-startup-wrapper-builder.ts`、`daemon/daemon-bash-shell-ready-rcfile.ts`、`powershell-osc133-bootstrap.ts` | shell 启动钩子树 |
| History/快照 | `src/main/daemon/terminal-history-*.ts`、`src/main/terminal-scrollback-snapshots.ts` | 两套互补的持久化 |
| Windows 件 | `src/main/windows/windows-pty-job.ts`、`windows-process-tree-kill.ts`、`daemon/daemon-host-relocation.ts` | job、taskkill、搬迁 |
| macOS 件 | `src/main/daemon/macos-daemon-{launchd,bundle}.ts` | 签名 helper + launchd |
| 持久化绑定 | `src/main/persistence/loading-store/pty-binding-*.ts`、`persistence/terminal-topology/` | pane/tab ↔ PTY 归属落盘 |
