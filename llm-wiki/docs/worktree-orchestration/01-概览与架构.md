# 第 1 章 · 概览与架构

> Orca worktree 编排子系统总览:它解决什么问题、由哪些层组成、入口在哪、Git 版本兼容怎么做。
> 本系列共 6 章,本章是地图;细节见后续各章。引用为仓库相对路径。

---

## 1.1 系统定位

Orca 的核心卖点是"一个 prompt 扇出到 N 个 agent,各自在独立 git worktree 里干活"。worktree 编排子系统是这件事的地基,负责五件事:

| 职责 | 章节 |
|---|---|
| **创建**:快速可靠地产出隔离 checkout(含投机预热) | [第 2 章](./02-创建管线.md) |
| **预备池**:把冷 `worktree add`(p50 ~4.1s)降到接近零 | [第 3 章](./03-预备池.md) |
| **删除**:多层护栏下的安全清理,后台化 + 崩溃恢复 | [第 4 章](./04-删除管线与安全护栏.md) |
| **身份**:路径复用、repo 删除重加、主机失联后身份依然正确 | [第 5 章](./05-身份命名与持久化.md) |
| **路由**:决定操作在哪台主机执行(本地 / SSH / WSL / runtime) | 贯穿各章 |

它在 `src/main` 下由 60+ 个文件组成,是仓库中最大的单一领域。文件数量本身说明一件事:**这个领域在生产中踩过大量坑**——几乎每个护栏都能追溯到一个 bug 编号,代码里用 "Why" 注释把教训固化了下来。

## 1.2 术语表

| 术语 | 含义 |
|---|---|
| **workspace root** | Orca 存放某项目所有 worktree 的根目录(可扁平/嵌套) |
| **preparation / prepared checkout** | 预备池条目:提前建好的隐藏 checkout,等待被创建流程"收养" |
| **claim** | 创建流程对某个 preparation 的独占认领 |
| **base / canonical base** | 创建所基于的分支;canonical 化后 `main` 与 `refs/heads/main` 等价 |
| **base family** | 同一分支的本地拼写与 remote-tracking 拼写(`main` ~ `origin/main`) |
| **execution host** | 实际操作 git/文件系统的主机:`local`、`ssh:<target>`、`runtime:<env>`、`wsl:<distro>` |
| **retired name** | 被某个 agent 使用过的自动生成名字,永久退休不再分配 |
| **lineage** | worktree 之间的父子血缘(UI 展示 fork 关系) |
| **instanceId** | 每次创建轮换的 UUID,防路径复用导致的元数据错配(ABA) |
| **scan generation** | 每 repo 单调递增的扫描世代号,防过期扫描结果被当权威 |
| **Orca provenance** | 元数据中的 `orcaCreatedAt` 等字段,证明"这目录是 Orca 建的" |
| **admission tier** | git 进程准入优先级:`interactive` > `status` > `background` |
| **catalogVersion** | `{ epoch, sequence }`,客户端跨重启排序 catalog 出版物 |

## 1.3 触发入口(三条路,殊途同归)

| 入口 | 位置 |
|---|---|
| 渲染进程 IPC | `src/preload/api/worktrees-bridge.ts:29` → `window.api.worktrees.create/remove/prefetchCreateBase` |
| 桌面 IPC handler | 创建 `ipc/worktrees/create/register-worktree-create-handlers.ts:38`;删除 `.../removal/register-worktree-removal-handlers.ts:131`;预热 `register-worktree-prefetch-handler.ts:10` |

## 1.5 执行主机路由:全系统的元规则

这是理解整个子系统的前提,所以放在概览里讲。

**规则一:主机身份只在一个地方解析。** 永远用 `getRepoExecutionHostId(repo)`,绝不直接用 `repo.connectionId`。来自 bug #11163:一个只有 `executionHostId: 'ssh:<target>'` 的 repo 行,曾导致对远程路径在**本地**跑 `git worktree add`(创建侧)和"删了同名本地目录而元数据按 `ssh:<target>` 剪除"(删除侧)。

**规则二:远程主机一律抛错,绝不回退本地。**

| 主机 | 创建 | 删除 | 列表 |
|---|---|---|---|
| `local` | 本地执行 | 本地执行 | 本地执行 |
| `ssh:` | `SshHostNotServedError` | 抛错 | `WorktreeCatalogUnavailableError` |
| `runtime:<env>` | `ExecutionHostNotDispatchableError` | 抛错 | `WorktreeCatalogUnavailableError` |

**规则三:失联不是证据。** "Loss of contact is never evidence that the checkout is local";列表宁可抛错也不返回 `[]`——空调用方会把空列表当权威结果剪除还活着的元数据(#1158、#14004、#18272)。

**规则四:unverifiable 永不授权删除。** 路由解析不出执行主机的 home 目录时,一切删除授权门 fail-closed(详见第 4 章 §4.7)。

## 1.6 Git 版本兼容层

### 基线与策略

事实基线 **Git 2.25**(`worktree move -f -f` 需要它,`git/worktree-create-preparation.ts:207` 注释;`worktree-list-reader.ts:95` 称 2.25 为 "the baseline")。**没有硬版本门**——策略是逐命令能力探测 + 缓存 + 回退。

### GitCapabilityCache(shared/git-capability-cache.ts:7-20)

跟踪 7 项能力:`worktree-add-lock-reason`、`worktree-list-z`、`rev-parse-path-format`、`fetch-no-write-fetch-head`、`for-each-ref-exclude`、两个 `merge-tree` 能力。

- 探测失败 **30 分钟后重试**——原地升级 Git 不用重启 Orca
- 缓存**按执行主机隔离**(`local` / `wsl:<distro>`,LRU 128,`git/git-capability-state.ts:23-41`);WSL linked-worktree 路由可切换由哪台主机的缓存回答(:43-63)

### 具体回退

| 首选 | 回退 | 位置 |
|---|---|---|
| `worktree list --porcelain -z` | 行解析 + admin-dir 锁标注 + 逐路径存在性探测(Git <2.31 的 `prunable`) | `worktree-list-reader.ts:220-255` |
| `rev-parse --path-format=absolute` | 裸 rev-parse + **echo 检测**(老 Git 忽略未知 flag 还退出 0) | `worktree-list-reader.ts:70-73` |
| `worktree add --lock --reason` | 裸 add + 手动 `wx` 独占写锁文件 | `worktree-preparation-add.ts:69-110` |

错误检测与 locale 无关:exit 129 或对 "unknown/invalid/unrecognized option" 的正则(`shared/git-worktree-command-capabilities.ts:18-39`)——**不能匹配本地化的错误消息文本**。

### 准入优先级(与创建/预备的关系)

```
interactive(用户交互的创建/删除)
   > status(预备池构建等投机工作)
   > background(stale 清理等卫生工作)
```

机制:AsyncLocalStorage 传播 tier(`git/command-runner/git-operation-executor.ts`),调度器带 15s 老化防饿死(`shared/git-admission-scheduler.ts`)。详见第 2 章 §2.7。

## 1.7 一张图看懂创建与删除

```
创建(第 2、3 章)                          删除(第 4 章)
─────────────                            ─────────────
composer 打开                             用户点 Delete / CLI
  └ prefetch: fetch + 预备 checkout        ├ 查 pending 后台删除 → join
    (.orca-preparing/, 锁 + TTL 5min)      ├ in-flight 合并(optionsKey!)
用户确认                                   ├ per-repo 验收串行队列(#2259)
  ├ 路由检查(ssh/runtime 抛错)            ├ 严格列表 + 安全栈
  ├ base 解析 + 刷新启动(不 await)        │   (危险路径/home/嵌套/孤儿证明)
  ├ resolve_name(100 次后缀循环,         ├ archive hook(硬前置,#19334)
  │   查退休名/分支冲突/pending 删除)      ├ 重校验 + watcher gate + 停 PTY
  ├ await base 刷新                        ├ git worktree remove(无超时,p90 29s)
  ├ git_worktree_add                       │   或 detach 成后台删除
  │   ├ hit: 认领预备 → finalize           │   ├ 记录先于删除落盘(WAL, 2s 预算)
  │   │   (move -f -f + checkout -b)       │   ├ quit abort,记录保留,重启续删
  │   └ miss: git worktree add             │   └ 失败入 failedWorktreeRemovals
  ├ instanceId 轮换 + lineage              ├ 分支删除(merged-only, per-repo 串行)
  ├ 退休生成名(成功和回滚失败都退)        └ 元数据清理 + 世代号 bump
  └ finally: timing.finish() → rearm.fire()
```
