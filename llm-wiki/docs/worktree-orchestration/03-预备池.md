# 第 3 章 · 预备池(Prepared-checkout Pool):投机执行核心

> 作用域:worktree 创建时的"投机预热"机制——新建 worktree 对话框打开期间,后台预先做一次完整 checkout(隐藏、锁定、detached);真正创建时"认领 + 移动改名",把一次冷 `worktree add`(实测 p50 约 4.1s)降到接近零。
>
> 本章是全系统最精巧的部分,也是学习并发设计最好的样本。所有引用为仓库相对路径。

## 3.1 池数据模型

### 常量(`worktree-create-preparation-pool.ts:45-46`)

```ts
export const WORKTREE_CREATE_PREPARATION_TTL_MS = 5 * 60_000
export const WORKTREE_CREATE_PREPARATION_LIMIT = 3
```

TTL 5 分钟;**全局**最多 3 个预备检出(跨所有仓库——这是磁盘占用上限的语义)。

### `PreparationEntry` 字段(pool.ts:48-67)

| 字段 | 含义 |
|---|---|
| `key` | 池 Map 键(见下) |
| `repoPath` / `repoPathKey` | 仓库路径原文与规范化键(Windows 大小写折叠) |
| `workspaceRoot` / `workspaceRootKey` | worktree 根目录(`.orca-preparing` 藏在它下面) |
| `wslDistro` | WSL 发行版名,`''` = 宿主机。**distro 决定根目录在哪个文件系统上**,所以是 key 的一部分 |
| `baseBranch` | prefetch 武装时的原始拼写(如 `origin/main`) |
| `canonicalBase` | 规范化后的 ref(如 `refs/remotes/origin/main`),key 的一部分 |
| `preparedPath` | 隐藏 checkout 路径:`{workspaceRoot}/.orca-preparing/{pid}-{uuid}` |
| `lockReason` | Git 锁 reason,即**所有权证明** |
| `createdAt` | 驱逐按它排序 |
| `ready` | 构建(或最新 tip 刷新)完成的 Promise |
| `expiration` | TTL 句柄(`expiration.unref()`,pool.ts:227——不阻止进程退出) |
| `controller` | `AbortController`,与 `options.signal` 经 `AbortSignal.any` 合并 |
| `checkoutStarted` | 是否真的执行过 checkout;决定丢弃时是否有东西可删;锁丢失时重置为 false |
| `activity` | origin(prefetch / rearm / rearm_then_prefetch)、buildMs/idleMs、磁盘工作计数。"Recording only; never gates the pool" |

### Map 键(`worktree-create-preparation-claim.ts:39-55`)

```ts
/** Case-folded on Windows, so the arming and claiming sides key on the same path. */
export function preparationPathKey(path: string): string {
  if (isWindowsAbsolutePathLike(path)) {
    return win32.normalize(path).toLowerCase()
  }
  return posix.normalize(path)
}

/** Keyed on the canonical base so the prefetch and the create agree when they spell the same ref
 *  differently; a genuinely different ref still gets its own entry. */
export function preparationEntryKey(repoPathKey, workspaceRootKey, canonicalBase, wslDistro) {
  return `${repoPathKey}\0${workspaceRootKey}\0${canonicalBase}\0${wslDistro}`
}
```

### 驱逐算法(pool.ts:99-122)

注释即设计意图:"Bound full-checkout disk use, evicting the requesting workspace's oldest preparation first."

```ts
while (preparations.size >= WORKTREE_CREATE_PREPARATION_LIMIT) {
  const byAge = [...preparations.values()].sort((l, r) => l.createdAt - r.createdAt)
  const victim =
    byAge.find((e) =>
      e.repoPathKey === repoPathKey &&
      e.workspaceRootKey === workspaceRootKey &&
      e.wslDistro === wslDistro
    ) ?? byAge[0]
  preparations.delete(victim.key); clearTimeout(victim.expiration)
  victim.controller.abort(); discardEntryInBackground(victim)
}
```

满 3 个时,先淘汰**同一 (repo, workspaceRoot, distro)** 内最老的(惩罚制造压力的人),没有才淘汰全局最老。过期走 `expireEntry`(pool.ts:90-97):仅当 `preparations.get(entry.key) === entry`(防误删同名新 entry)才删、abort、后台丢弃。

`hasPendingPreparations`(pool.ts:81-83)= 池非空 || 有认领 || 有 stale 清理在途;被 `repo-maintenance-idle-gate.ts:34` 用来暂停 repo 维护(gc 等)——"A prepared checkout is a create that is either in flight or imminent."

## 3.2 武装(Arming)流程

### 入口链

`prepareWorktreeCreateForRepo`(worktree-create-preparation.ts:104-113)→ `worktreePreparationGit.run(...)`(低优先级准入层)→ `prepareWorktreeCreateInBackground`(:115-142):

1. **跳过条件**(:121-123):`repo.connectionId`(SSH)或 folder repo 直接 return。
2. `workspaceRoot = await computeWorkspaceRootAsync(...)`——注释说明 WSL 语义:

   > "Resolving a WSL repo's root spawns `wsl.exe`, and this runs while the create composer is open, so it must not block the main thread. Key lookup and insert stay in one sync run after the await. The mirror distro must be threaded exactly as createLocalWorktree threads it, or the two sides key on different roots and every prepared checkout is discarded."

3. `canonicalBase = await canonicalBaseRef(...)`——把 `main`/`origin/main` 规范成 `refs/heads/...` / `refs/remotes/...`。
4. `startPreparation(...)`。

### `startBackgroundPreparation`(pool.ts:203-283)

1. 算 key、`enforcePreparationLimit` 驱逐。
2. `preparationId = ${process.pid}-${randomUUID()}`;`lockReason = createWorktreePreparationLockReason(preparationId)`。**路径里嵌 pid** 供崩溃后清理判断 owner 死活。
3. 隐藏路径:`<workspaceRoot>/.orca-preparing/<pid>-<uuidv4>`(`WORKTREE_CREATE_PREPARATION_DIRECTORY`,shared/worktree/create-preparation.ts:1)。
4. `entry.ready` 异步体:
   - 先 `startStalePreparationCleanup(...)`——每个新预备顺带做同主机崩溃残留清理(见 §3.9);
   - `mkdir -p` 隐藏目录;
   - `prepareWorktreeCreateCheckout(repoPath, preparedPath, canonicalBase, lockReason, options, beforeMaterialization)`;
   - 失败且为 `WorktreePreparationLockOwnershipError` → `checkoutStarted = false`(**锁是别人的 → 磁盘不是我们的,丢弃侧要跳过**)。
5. 失败兜底(:276-281):entry 仍在池中则移除并清 TTL——失败条目立刻不可被认领。

### Git 侧 `prepareWorktreeCreateCheckout`(git/worktree-create-preparation.ts:34-93)

- 全程 `withRepoRefMaintenancePaused('worktree-prepare', ...)` + `runWithGitReadCacheInvalidation(...)`。
- `resolveWorktreeAddBaseRef`(shared/worktree/base-ref.ts:3-25):已是 `refs/` 开头直接用;含 `/` 的短名先试 `refs/remotes/` 再试 `refs/heads/`;裸名只试 `refs/heads/`(注释:短名可能与 tag 冲突,按 base picker 的命名空间偏好解析)。
- `addLockedWorktreePreparation`(git/worktree-preparation-add.ts:47-58):

  ```
  git worktree add --detach --no-checkout --lock --reason <lockReason> <path> <baseRef>
  ```

  三个 flag 各司其职:`--detach` 不建分支(分支名归最终创建方);`--no-checkout` 不物化文件(后面 reset 才物化);`--lock --reason` 出生即锁定并写入所有权证明。

  **旧 Git 回退**(:64-117):经 `GitCapabilityCache` 探测,若不支持 `--reason`,回退为裸 `add` 后手动 `wx` 写锁文件。清理边界注释(:77):"A canceled add can leave its marker; a pre-existing checkout is never ours to remove."
- **验锁 #1**。
- **`beforeMaterialization` 语义**(:63-73):这是 prefetch 阶段发起的 base fetch promise。先挂一个 `catch(()=>{})` 防 unhandled rejection(:42 注释:"Observe early rejection while registration runs; awaiting still reports the original error."),等 fetch 落定 → **验锁 #2** → `rev-parse` 取新 tip → **验锁 #3**。来源注释(worktree-create-base-prefetch.ts:99):"Register during fetch, then materialize the settled base once; offline keeps its local tip."
- 物化(:74-78):

  ```ts
  // Why: reset materializes files without running user post-checkout hooks before submit.
  git reset --hard <materializationBase>
  ```

  用 `reset --hard` 而非 checkout,是为了**不触发用户的 post-checkout 钩子**——投机工作不该以用户身份产生副作用。
- reset 后**验锁 #4**。
- 中途失败:只要不是锁所有权错误,`performDiscardPreparedWorktree` 自清理后 rethrow。

## 3.3 认领(Claim)协议

### `PreparationRequest.canonicalBase` 的懒求值设计(claim.ts:33-35)

> "`null` until the caller has paid the ref probe. A raw-base match resolves without it, so the common hit spawns no git at all."

——常见命中(拼写一致)**完全不 spawn git 进程**。

### `selectPreparationForCreate` 决策表(claim.ts:82-130)

纯同步函数,完整决策顺序:

| 步骤 | 条件 | 结果 |
|---|---|---|
| 1 | 池空 | miss `none_armed` |
| 2 | 无同 repoPathKey 者 | miss `repo_mismatch`(:91 注释:"Separate from `none_armed`: this is what a size-cap eviction looks like from the create side.") |
| 3 | 无同 wslDistro 者 | miss `wsl_distro_mismatch`(:94:"Distro before root: the distro decides which filesystem the root is even on.") |
| 4 | 无同 workspaceRootKey 者 | miss `workspace_root_mismatch` |
| 5a | `canonicalBase === null` 且 raw 拼写相同 | **exact**(:109:"Same spelling, so the armed entry already holds this request's canonical form.") |
| 5b | `canonicalBase === null` 且无 raw 匹配 | **needs-canonical-base**(调用方付费做 ref 探测后再来) |
| 6 | canonical 相同 | **exact** |
| 7 | 同 family 候选存在 | **retarget**,取 `createdAt` 最新者(:122-124) |
| 8 | 其余 | miss `base_mismatch` |

函数级 docstring(:67-81)是整个机制的浓缩:

> "The two sides of the pool disagree in practice — the prefetch arms `origin/main` while the create resolves `main`, or vice versa — and an exact-string key turns every such disagreement into a silent cold create. Canonicalizing catches the spelling differences; the base-family retarget catches the local-vs-remote-tracking ones… The bound matters: refs outside the same branch family are rejected, because a retarget across unrelated history degenerates into a full checkout and wins nothing. **Synchronous on purpose: the caller claims the returned entry in the same run, so two concurrent creates cannot both walk away with the same prepared checkout.**"

### `takePreparation`(pool.ts:139-154)

```ts
preparations.delete(entry.key)
clearTimeout(entry.expiration)               // 被认领后不再受 TTL 约束
const requestedKey = preparationEntryKey(...requestedCanonicalBase...)
return registerClaim(entry, requestedKey)    // 进认领登记表
```

注意 `requestedKey` 用**请求方**的 canonical base 构造(retarget 时与 entry.key 不同)——两个拼写方向的后续武装请求都能挂到这个 claim 上。

### `reservePreparation`:await 后重读模式(reservation.ts:32-96)

注释(:31):"Selection through take, so the take stays in the same synchronous run as the last selection."

流程:

1. 先用 `canonicalBase: null` 选一次(零 git)。
2. `needs-canonical-base` → **await ref 探测**(:47-48 注释:"The probe is the only await here, and the pool is re-read after it, so the select-and-take below stays one synchronous run and no other create can hold the same entry.")→ **重新 `listPreparations()` 再选**。
3. retarget 候选 → **await `measureRetargetDivergence`** → 通过后才可用;之后**第三次重读池**:

   ```ts
   // Re-select after the walk: the pool may have gained an exact match or lost this entry. A
   // different retarget candidate is left for the next create rather than claimed unverified.
   ```

   候选被换/消失 → 宁可 miss 也不认领未验证的候选。
4. 全部通过 → `takePreparation`,返回 `{status:'reserved', entry, reservation, retargeted, canonicalBase}`。

**模式提炼**:每次 await 都是并发窗口;最后一次 select 必须与 take 在同一同步回合。

## 3.5 Retarget(换基)

### Base family(shared/worktree/base-ref.ts:27-52)

> "The branch identity two base refs share when one is the local branch and the other is a remote-tracking copy of it: `refs/heads/main` and `refs/remotes/origin/main` both return `main`. Bounds the prepared-checkout retarget… Anything unqualified — a bare name, a commit id — has no family."

`refs/remotes/<remote>/HEAD` 返回 null(:48:"a symbolic pointer, not a branch identity")。

### `measureRetargetDivergence`(git/worktree-base-divergence.ts:145-177)

**上限**:`RETARGET_MAX_COMMIT_DIVERGENCE = 100`(:32)。docstring(:23-31)给了实测依据:

> "Measured on a 21,715-file repo: a local `main` and its `origin/main` were 5 commits and 74 files apart, while an abandoned fork's `main` — same branch name, so the same base family — was 8,173 commits and 21,708 files from `origin/main`, i.e. a whole-tree checkout. A commit count separates those by three orders of magnitude, so it is the cheap proxy for the tree diff the retarget reset would have to write."

——**同 family ≠ 接近**。被遗弃 fork 的 `main` 可能差整棵树,所以 family 之内还要按提交数卡界。

**预算**:`RETARGET_DIVERGENCE_BUDGET_MS = WSL 环境等待 + 500ms` headroom(:60-61)。要点:端到端 deadline(不是每条命令超时);对照物是 ~4.1s p50 冷 `worktree add`——"this exists only to decide whether to skip a ~4.1s p50 cold `worktree add`, so when it expires the create pays the budget and then does that add anyway"。

**算法**(顺序有讲究):

1. 合并取消信号:`abortSignalWithTimeout(options.signal, budget)`——取消创建立即停止探测。
2. **双向** `rev-list --count --max-count=101 from..to` 并行(:157-158:"Both directions: commits the target adds decide what the reset writes, commits only the preparation has decide what it must delete.")。`--max-count` 让不相关历史只花有界代价。
3. 任一方向失败 → `'unknown'`。
4. `ahead + behind > 100` → `'exceeded'`。
5. **最后才 `merge-base`**(:168-171):"Only now: `merge-base` has no `--max-count`, so on unrelated histories it would walk both of them in full. Reaching here already proved neither side is more than the cap ahead of the other, which bounds that walk."
6. 有共同历史 → `'within'`,否则 `'exceeded'`。

**三值语义**(:17-21):

> "`unknown` is deliberately not folded into `exceeded`: "the bound says no" and "the bound could not be evaluated" have different causes and different fixes… `unknown` covers a blown deadline, a cancelled create, and an ordinary Git failure alike — it is "no answer", not "slow"."

函数整体 fail-closed(:139-144):"only a positive `within` authorizes reusing the checkout, so every other outcome lands on the cold create path."

## 3.6 Finalize:`finalizePreparedWorktree`(git/worktree-create-preparation.ts:134-281)

认领成功、构建完成后,把隐藏 checkout 变成正式 worktree 的过程。**每个破坏性 Git 步骤前都重新验锁**,全程共 **6 次**所有权验证:

| 步骤 | 操作 | 前置验锁 |
|---|---|---|
| 1 | 定位 lockPath(`verifyWorktreePreparationLock`) | #1 |
| 2 | 并行读目标 base commit 与 prepared HEAD(`Promise.allSettled`,:181:"Settle both reads before failure cleanup can remove the prepared checkout.") | — |
| 3 | 漂移则 `reset --hard targetHead`(:190-197)——同时覆盖"base 移动了"和"retarget"两种情况 | #2 |
| 4 | `git worktree move -f -f <prepared> <target>`(:203-215) | #3 |
| 5 | `git checkout --no-track -b <branch> <targetHead>`(就地建分支) | #4 |
| 6 | 写 base 配置、upstream、`push.autoSetupRemote` | #5 |
| 7 | `unlockWorktreePreparationAtPath`(内部先再验 reason 再 `unlink`) | #6 |

关于第 4 步的双 force(:203):

> "Why: `-f -f` moves the locked preparation while preserving its lock reason (Git >=2.25)."

第一个 `-f` 允许移动被锁定的 worktree;第二个 `-f` 移动时保留锁(不解锁、保留 reason)——锁 reason 随树活到最终路径,后续步骤才能继续做所有权验证。**这是 Git 2.25 成为全仓库基线版本的直接原因**。

第 3 步的调用方注释(worktree-create-preparation.ts:262-263):

> "Finalize resolves the requested base itself and resets the prepared checkout onto that commit, so a retargeted claim is handed over at the requested commit or not at all."

——retarget 的正确性不依赖认领时的假设:finalize 自己解析目标 base,要么交出精确落在请求 commit 的检出,要么报错走冷路径。

**失败模式**(:254-267):

- `WorktreePreparationLockOwnershipError` → **不清理**,直接抛(:297 注释:"Another owner holds the preparation's lock, so it is not ours to remove.")。
- 其他错误 → `removeFailedFinalization`(git/worktree-preparation-discard.ts:120-158):验锁后 `git worktree remove --force --force`(:103:"Double force requires a freshly verified ownership marker."),分支已挂上再 `git branch -D`。
- 调用侧返回 miss `finalize_failed`,走普通 `addWorktree` 冷路径,并照样 release claim。

## 3.7 锁机制(git/worktree-preparation-lock.ts)

**锁路径解析**(:43-69):`git rev-parse --git-path locked --git-common-dir`;注释(:53):"Newlines in a path make the combined response ambiguous; read each pointer separately."

**上锁**(:71-88):

```ts
// Git's own lock marker is a reason plus newline; exclusive creation preserves another owner.
await writeFile(lockPath, `${lockReason}\n`, { flag: 'wx' })
```

`wx` 排他创建:文件已存在 → 抛 `WorktreePreparationLockOwnershipError`——**绝不覆盖他人锁**。

**reason 格式**(shared/worktree/create-preparation.ts:1-8):

```
orca-create-preparation:v1:<pid>:<pid>-<uuidv4>
```

`parseWorktreePreparationOwnerPid` / `parseWorktreePreparationPathOwnerPid` 分别从 reason 和路径提取 owner pid(有严格 uuidv4 正则)。

**所有权证明的耐用性**(:32-42 注释,核心原则):

> "The Git lock reason is the durable ownership proof. A path can be chosen by a user (including for an uncommitted detached worktree), so path shape alone must never hide or force-remove it. A crash before locking may leave an unlocked detached entry for manual cleanup, but cannot delete user data."

——`isWorktreeCreatePreparation` 只看 lockReason,**路径形状绝不可作为隐藏或强删的依据**。

## 3.8 Re-arm(补货)与 Burst 检测

### `deferRearmPreparation`(worktree-create-preparation.ts:184-225),docstring 全段值得精读:

> "Replaces a just-consumed preparation, re-armed on the base the create actually used so the next one hits exactly — but only once the user has shown they are creating in a burst. A replacement costs a full checkout and ~5 minutes of disk until its TTL, so arming one after an isolated create spends that on nobody.
>
> Returns a thunk rather than launching: the replacement is a full `reset --hard`, which on a large repo holds a general admission slot for tens of seconds. Started mid-create it competes with the create's own git, so the caller runs it after materialization/startup completes."

要点:

- re-arm 用**创建实际使用的 base**(claim.canonicalBase)而非 entry 原 base——"so the next one hits exactly";
- 已有针对同一 canonicalBase 的延期 explicit prefetch 则不重复武装(explicit 优先);
- burst 记账在 thunk **创建时**做("so a later create is recognized as part of a burst")。

### Burst 检测(worktree-create-preparation-burst.ts)

```ts
export const WORKTREE_CREATE_BURST_MS = 5 * 60_000
// "Two creates this close together mean more are likely; an isolated create earns no replacement."

const previous = lastConsumedAt.get(key)
setBoundedMapEntry(lastConsumedAt, key, now, MAX /* 64 */)
return previous !== undefined && now - previous <= WORKTREE_CREATE_BURST_MS
```

**同一 preparation key 前后两次消费间隔 ≤ 5 分钟**才算延续 burst。第一次消费永远不算(:10-12:"A replacement checkout costs a full tree and holds disk until its TTL, so only a user who is already creating repeatedly earns one; the first create of a session pays nothing for a spare nobody claims.")。

### 为什么推迟到最外层 finally

`PreparationRearmHolder`(worktree-create-preparation.ts:56-58):"Carries the consumed slot's pending re-arm to the create's outermost `finally`, which fires it once — after startup on success, and on any failure that follows the consume."

本地创建路径(ipc/worktree-remote.ts:966-976)注释:

> "Why a holder fired in `finally`: consuming a prepared checkout leaves the pool one short, so a create that fails after that point — include copy, push target, terminal startup — must still arm the replacement. Fires exactly once, after startup on the success path."

且 `timing.finish()` 先于 `rearm.fire()`:"Closes the create's measured window first, so its own re-arm is not counted against it."——连遥测口径都考虑了。

## 3.9 卫生机制(Hygiene)

### Stale 清理(worktree-create-preparation-stale-cleanup.ts)

- **触发**:每次 `startBackgroundPreparation` 开头,key = (repoPathKey, wslDistro)。
- **单飞**:同 key 在途则只等扫描完;并发度 4。
- 回收 tier(:36-38):"Why 'background': reclaiming another process's leftovers is never what a user is waiting on, and removing a large tree holds a general admission slot for seconds."
- **判定链**:候选必须 lockReason 带 Orca 前缀;解析出 owner pid;`process.kill(pid, 0)` 只有 ESRCH 才算死。然后:
  - 已移动到最终路径且挂了分支(崩溃在 finalize 后半段)→ **只解锁,保留给用户**(:57-58:"Preserve a branch-attached final path after a crash; only detached or still-hidden preparations are safe to discard automatically.");
  - 仍是隐藏路径且路径 pid 与锁 pid 一致 → 丢弃。
- 调用方只等 `scanned`(:79:"do not make a new checkout wait for old file removal")。

### 丢弃重试(worktree-preparation-discard-retry.ts)

存在理由(:8-10):"Stale cleanup only reclaims preparations whose owner pid is dead, so a discard that fails inside the live process would strand its scratch checkout until the app restarts."——活进程自己的丢弃失败,stale 清理管不到,所以要有界重试(上限 3 次),挂到下次同 host 预备时顺带执行。

分流(:56-80):锁所有权错误 / orphan 错误 → 不重试("retrying that would only spawn Git to fail again");达上限 → warn 放弃("a path that never becomes removable must not tax every later preparation")。

### Tip 刷新(refresh queue)

**何时**:同一 key 已有 entry,再次 prefetch 且带 `beforeMaterialization`(base 刚被重新 fetch)→ 把隐藏 checkout 的 HEAD 推进到新 tip,保持认领时大概率无需漂移 reset。

`queuePreparedWorktreeTipRefresh`(worktree-preparation-refresh-queue.ts:7):"Publish the refresh before yielding so a racing create waits for the same checkout."——先把新 ready 链到 `entry.ready` 再返回,使并发 create 等的是刷新后的 ready。

刷新失败 = 该预备报废并后台丢弃;已认领的交给认领方处置。

## 3.11 端到端时序速查

```
1. 用户打开新建对话框
   → IPC worktrees:prefetchCreateBase
   → fetch base + prepareWorktreeCreateForRepo(beforeMaterialization = fetch 落定 promise)

2. 池:startPreparation
   → stale 清理 → mkdir .orca-preparing/<pid>-<uuid>
   → git worktree add --detach --no-checkout --lock --reason orca-create-preparation:v1:<pid>:<id>
   → 等 fetch → reset --hard <newTip>
   (TTL 5 分钟、全局上限 3)

3. 用户确认创建
   → consumePreparedWorktreeCreate → reservePreparation
     (raw 匹配零 git;否则一次 ref 探测;retarget 加分歧测量 ≤100 提交且有共同祖先)
   → 同步 takePreparation(出池、清 TTL、登记 claim)

4. await entry.ready(还在构建则等)

5. finalizePreparedWorktree:
   验锁 → 解析目标 base + 读 prepared HEAD → 漂移则 reset
   → worktree move -f -f 到最终路径 → checkout --no-track -b
   → 写配置 → 删锁文件
   (任一步锁验证失败 = 不清理、转冷路径)

6. 成功后 rearm thunk 挂 holder,最外层 finally fire:
   释放 claim(启动延期预备)+ burst 内则以本次实际 base 自动补货

7. 失败路径:prepare_failed / finalize_failed → 普通 addWorktree 冷路径,照样 release claim
```

## 3.12 本章设计要点回顾

1. **同步性代替锁**:select-and-take 同一同步回合,零锁零竞态(§3.3)。
2. **每次 await 后重读世界**:reservation 的三次重选(§3.3)。
3. **锁 reason 是唯一所有权证明**,路径形状什么都不是;丢锁 = 放弃一切清理权利(§3.7)。
4. **每个破坏性步骤前重新验证**:finalize 的 6 次验锁(§3.6)。
5. **投机有预算**:数量(3)、时间(5min TTL)、分歧(100 commits + 共同祖先)、频率(burst 门控)、优先级(status tier)五重封顶(§3.1/3.5/3.8)。
6. **失败方向全部偏向冷路径**:任何不确定都退化为普通 `worktree add`,绝不在不确定时使用预备检出(§3.5/3.6)。
