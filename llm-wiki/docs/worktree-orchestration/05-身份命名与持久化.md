# 第 5 章 · 身份、命名与持久化

> worktree 编排的"记忆系统":每个 worktree 是谁(身份)、叫什么(命名与退休)、系统重启后还记得什么(持久化与世代)。
> 这里的核心命题是:**路径会被复用,repo 会被删除重加,主机会失联——身份必须在这些事件后依然正确**。引用为仓库相对路径。

---

## 5.1 ID 体系与 instanceId:ABA 问题的解法

### 三层标识

| 标识 | 形式 | 作用 |
|---|---|---|
| worktree id | `<repo.id>::<path>`(worktree-remote.ts:1520) | 定位符(locator) |
| `instanceId` | `randomUUID()`,**每次创建轮换**(:1526) | 区分同一路径的不同 occupant |
| lineage parent | 指向父 workspace 的 instanceId | 血缘(fork 关系渲染) |

### 为什么需要 instanceId

```ts
// worktree-remote.ts:1525-1526
// Why: path-derived IDs can be reused after external deletion; rotate instance identity
// so stale lineage can't attach to the new occupant.
instanceId: randomUUID(),
```

场景:路径 P 上的 worktree A 被删,后来 worktree B 建在 P 上。若身份只由路径派生,B 会继承 A 的 lineage 和元数据——这是经典的 **ABA 问题**。解法:

1. 每次创建轮换 `instanceId`;
2. 当 lineage 父节点被**证实消失**时再轮换一次(worktree-lineage-pruning.ts:132-135)。

### 元数据的三层存储(persistence/loading-store/worktree-identity-metadata.ts:23-27)

1. `worktreeMeta` —— 按 locator key
2. `worktreeMetaByIdentity` —— 按逻辑身份
3. `worktreeIdentityAliases` —— 别名,让同一逻辑 workspace 在 id 拼写变化后存活

别名冲突按 `lastActivityAt` 然后 key **确定性**解决(:30-46)。

### 按主机限定,故意不回退(persistence/host-qualified-worktree-meta.ts:43-54)

`readWorktreeMetaForHost` **故意不 fallback** 到 locator 读法——跨主机读到错误元数据比读不到更糟。

### 元数据所有权(worktree-metadata-ownership.ts:16)

repo 拥有某 meta 行当且仅当:它是该 repo id 的唯一拥有者,或行的 `hostId` 匹配。删除安全读取 Orca provenance key 判断未注册目录是否 Orca 所建;`stripOrcaProvenanceMetaUpdates` 阻止伪造(见第 4 章 §4.6)。

`worktree-removal-repo-owner.ts:42-58` 的代理判断是有意的过度保守:"Fail-safe direction: **over-preserving leaves stale records, under-preserving destroys another host's live state.**"

## 5.2 生成名退休:一个伪装成命名问题的分布式系统问题

### 动机

agent 的历史(session、profile)**按路径组织**。同一路径被不同 workspace 复用会串历史。所以自动生成的名字(creature 名字,552 个海洋生物名组成的池)**一经使用永久退休**:

> "Retirement is permanent — a spent name's directory may still hold agent conversation state keyed by that path — so the registry can never evict. It compacts instead."(shared/worktree/retired-name-registry.ts:1-16)

注册表用 `exhaustedTiers` 水位线 + 显式 names 集合压缩存储。`creatureNameTier` 对非池名/重复后缀名返回 null——(:31-33):"Load-bearing for user-typed names: `fix-login-2` must not read as retired just because tier 2 is spent."

### 退休时机:成功 AND 回滚失败

- 成功路径(worktree-remote.ts:1491-1494):"Why: fallible metadata work after creation must not leave a real workspace name reusable."
- 失败路径(:1480-1485):仅当错误带 `cleanupFailed === true`(worktree-name-retirement.ts:75-84:"A sparse create error carries this marker only when its rollback also failed, leaving the path occupied even though creation rejected.")
- 只持久化规范生成名(:70-73):"Only canonical generator output is persisted. Collision retries advance canonical tiers, so a repeat-suffixed path can never be generated again and needs no permanent registry entry."

### 双存储:repo.id + namespace(worktree-retirement-namespace.ts:10-18)

> "Primary storage stays on `repo.id`... the namespace is derived from settings that a user can toggle at any time, so keying storage on it would orphan every affected repo's retirements on a settings change. This map is the second, path-derived copy — **a settings toggle changes this key but `repo.id` still holds the tombstone, and a remove/re-add loses the `repo.id` row but this key still matches**."

读侧取两者并集(name-retirement.ts:167-181):"Neither alone survives both events."

### namespace key 推导

- `retirementHostIdentity`(namespace.ts:33-41):非 ssh → hostId;**ssh → endpoint 元组** `ssh:${sshEndpointKey(target)}`(host|port|user),查不到 → `UNKNOWN_SSH_HOST_IDENTITY`。注释(:30-32):

  > "SSH resolves to the endpoint tuple rather than the target row id, because **a removed and re-added host mints a fresh id while reaching the same filesystem**."

- `retirementNamespaceKey(hostIdentity, probePath)` = `hostIdentity:worktreePathComparisonKey(probePath)`;probePath 用特殊名 `orca-retirement-probe` 计算,代表"该 repo 创建工作区的 cwd 命名空间"。
- `getRetirementCollisionKey`(:121-153):"Two repos that would place a workspace of the same name at the same path share retirements; independent paths do not." 有 512 上限 cache;(:142-143):"Why not always cache: only the WSL home *success* path is cached upstream, so a stopped distro yields a fallback namespace. Memoizing that would strand the repo there for the whole session."

### UNKNOWN_SSH_HOST_IDENTITY:故意的过度退休(namespace.ts:25-28)

> "No target row means no way to tell endpoints apart. The retirement contract prefers **over-retiring (one name out of a 552-name pool) to reissuing a path whose agent history is still there**, so unresolvable SSH repos share a bucket — still split by workspace path."

### peer-repo 合并(name-retirement.ts:183-234)

> "Stored per repo id, which is stable, but read across every repo that creates into the same cwd namespace — **that is where a reissued name would actually collide**. The peer scan is deliberately lazy: a repo's own retirements never touch a path, and a peer's namespace is derived only once that peer is known to hold retirements."

### 磁盘回填(:276-307)

扫描 workspace 根目录和 Claude profile 历史目录恢复退休名。两个要害注释:

> "Remote workspaces keep their agent state on the execution host, which this scan cannot see, so a re-added remote repo does not recover its retirements the way a local one does."
> "Why the host id and not `connectionId`: a runtime-owned repo carries `executionHostId` with no `connectionId`, so a connectionId check calls it local, scans THIS machine's directories, and files the result under the runtime's namespace — retiring names never used there while missing the ones that were."

回填是异步的(:276-278):"this runs on composer open, not just at create time, and the sync probe would resolve a WSL home with a blocking `wsl.exe` call — **up to 5s of frozen main process on a stopped distro**."

### on-demand runtime 豁免(:243-250)

> "On-demand runtimes are the exception: the address is part of the key and changes on every provision, so a mirror written here is unreadable after the next one while still minting a namespace per run — spending the capped slots that local and SSH projects depend on."

## 5.3 Lineage 与剪枝

`worktree-lineage-pruning.ts:51` 剪除"被证实消失"的 worktree 血缘边,守卫:

- **一次空列表不能证明批量消失**(:72-78)
- WSL move 阻塞剪枝

## 5.4 扫描世代(local-worktree-scan-generation.ts)

### epoch UUID(:6-9)

> "Why per process: generations restart with the process, so a client ordering catalog publications across a host restart must see the restart as a new catalog, not an older one."

`LOCAL_WORKTREE_CATALOG_EPOCH = randomUUID()`;`catalogVersion = { epoch, sequence: generation }`(:12-14)。

### per-repo generation(:21-34)

全局 `generationSequence` 单调递增;**每次变更都 bump**;`retireLocalWorktreeScanGeneration` = bump + forget。

效果:**开始于创建/删除之前的扫描结果,永远不会被当作最新结果服务或缓存**。

### mutationRevision(:45-58)——为什么不用 generationSequence

> "Advances on every event above that can change what a worktree scan would find — repo add, removal, update, and scan-cache invalidation — and on nothing else. A cache that must not answer for repos it never saw compares this in O(1) instead of walking the repo list.
> **Why not `generationSequence`: that also advances when `getLocalWorktreeScanGeneration` mints a key for a repo id nothing has scanned yet, which is a read.** Keying a snapshot on it would let a read path discard a snapshot that is still perfectly valid.
> Ordering-only: the value means nothing outside a same-process comparison."

——读路径绝不能推进失效计数器,否则"读"会使有效快照失效。

### 创建/删除回复携带 catalogVersion

客户端可跨重启排序出版物(register-worktree-removal-handlers.ts:50,119)。

## 5.5 元数据剪枝门(local-worktree-metadata-prune-gate.ts,#17775)

### 问题背景(:1-24)

> "on a store whose dangling rows outnumber live worktrees **~100:1** it re-derives an answer it already has, forever, pinning the main process in filesystem completion callbacks (#17775). Rows pinned by a persisted session are never removable, so the repetition cannot even make progress."

### 解法:证据门控,永不时钟驱动

三种证据信号:

1. 该 repo 的 worktree 生命周期事件 → `requireLocalWorktreeMetadataPrune(repoId)`
2. 使某行"**更可删**"的变更(meta/identity/lineage 行删除,session/lease 释放)→ 全局 `pruneInputsGeneration += 1`
3. Git 列表指纹变化(排序后 NUL 连接作指纹)——(:74-75:"Why not on the first listing: a repo we have never scanned is already due by default... Re-arming here would double it.")

### 为什么只有"更可删"的变更计数(:17-20)

> "the listing path itself writes worktree metadata (discovery backfill, host-ownership stamping), so bumping on every metadata write would **re-arm the gate from the very scan it gates and restore the storm**. Additions and updates can only preserve more rows, so staleness there is harmless."

——被门控的扫描自己会写元数据;如果"写"也算信号,门会被自己的扫描重新武装,风暴回归。

### 保守失败方向(:22-24)

> "The failure direction is deliberate. A signal we miss leaves a dangling row in place until the next one arrives — **hygiene lags, and nothing is deleted that would not have been deleted anyway**."

### 其他细节

- `markLocalWorktreeMetadataPruneStarted`(:36-43)在**捕获 expectation 时**记录而非完成时:"a scan that is invalidated or fails mid-flight must not re-arm the full capture on the very next listing poll"
- `retireLocalWorktreeMetadataPruneStateForRepo`(:93-103):任何形态的移除都可能解 pin 其他 repo 的行,故总是全局 invalidate

### 列表失败的语义(repo-worktrees.ts:60-83)

`listRepoWorktreesForDetectedScan` 在 git 失败时**拒绝**,而不是返回 `[]`;`assertLocalGitRoute` 对 ssh/runtime 抛 `WorktreeCatalogUnavailableError`(#1158、#14004、#18272)——**失败的扫描不能被发布成"权威的空列表"去剪除一切**。

## 5.6 本章设计要点回顾

1. **身份与时间解耦**:locator 可复用,instanceId 轮换防 ABA(§5.1)。
2. **双写抗单点丢失**:退休注册表 repo.id 行 + namespace 行,各扛一种丢失场景(删除重加 / 设置变更)(§5.2)。
3. **宁多勿漏的退休**:UNKNOWN bucket 故意过度退休——552 个名字的池子,浪费一个好过复用一个带历史的(§5.2)。
4. **读不推进失效**:mutationRevision 与 generationSequence 分离,读路径永不使快照失效(§5.4)。
5. **破坏性维护必须证据门控**:剪枝由事件驱动而非时钟,且只认"更可删"方向的信号——否则门会被自己的扫描喂饱(§5.5)。
6. **失败方向一律保守**:hygiene lags 是可接受的,误删是不可接受的(§5.5)。
