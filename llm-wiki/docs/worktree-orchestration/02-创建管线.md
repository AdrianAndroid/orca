# 第 2 章 · 创建管线:从 IPC 到 `git worktree add`

> 主流程 `performLocalWorktreeCreate`(`src/main/ipc/worktree-remote.ts:957-1766`,约 800 行编排代码)。
> 本章按代码执行顺序逐阶段拆解,含全部计时/遥测机制。引用为仓库相对路径。

## 2.0 入口包装:`createLocalWorktree`(worktree-remote.ts:957-976)

```ts
return worktreeCreateGit.run(async () => {   // interactive 准入层,见 §2.7
  ...
  } finally {
    timing.finish()   // 先关闭计时窗口
    rearm.fire()      // 再触发预备池补货(恰好一次)
  }
})
```

finally 的顺序有讲究(:965-967):

> "Why a holder fired in `finally`: consuming a prepared checkout leaves the pool one short, so a create that fails after that point — include copy, push target, terminal startup — must still arm the replacement. Fires exactly once, after startup on the success path."

且 `timing.finish()` 先于 `rearm.fire()`——先关闭计时窗口,**本次创建自己的 re-arm 不会被计入它的耗时**(worktree-create-timing.ts:25-26)。

**两阶段进度 spinner**(:939-940):

> "Why: two-phase spinner — fire 'fetching' before pre-create fetch and 'creating' before git worktree add so the renderer can swap its label. `checkout` carries git's checkout meter during 'creating'; null means the checkout finished."

## 2.2 命名阶段(`resolve_name`,:1166-1308)

### 循环结构

上限 `WORKTREE_CREATE_MAX_SUFFIX_ATTEMPTS = 100`(worktree-create-candidates.ts:8):

```ts
for (let suffix = 1, attempts = 0; attempts < WORKTREE_CREATE_MAX_SUFFIX_ATTEMPTS; suffix += 1)
```

注意 `suffix` 和 `attempts` 是两个计数器:**退休名跳过时不消耗 attempts**(:1189-1192)。

### 每轮检查顺序

**① 生成候选名**(:1177-1188):
- 普通名:`suffix === 1 ? value : `${value}-${suffix}``
- 生成名走 **tier 制**:`getGeneratedWorktreeCreateRetryCandidate(value, suffix-1, exhaustedTiers+1)`(shared/new-workspace/worktree-create-retry-policy.ts:53-63)——解析出 `{poolName, tier}` 后取 `creatureNameAtTier(poolName, max(tier, minimumTier) + attempt)`

**② 退休名跳过**(:1189-1191):`if (isRetiredName?.(name)) { continue }`(注册表加载条件:`nameWasGenerated && isGeneratedWorktreeCreateName`)。

**③ 解析分支名**(:1195-1204):override 分支需过 `git check-ref-format --branch` 且不得以 `-` 开头;无 override 走 `computeValidatedBranchName`。注释(:1171):"Why: a create-from-review branch override may already exist locally; suffix both branch and path instead of blocking the user."

**④ checkoutExistingBranch 判定**(:1205-1231):显式选择的分支(`branchNameOverride` 或用户选了已有本地分支)走"收养优先":

```ts
const preferExistingBranch = Boolean(args.branchNameOverride || selectedExistingLocalBranchName)
checkoutExistingBranch = preferExistingBranch && (await tryExistingBranch())
```

`canCheckoutExistingLocalBranch`(:462-499):分支存在 + base commit 与该分支头相等 + 没有别的 worktree 正检着它。收养后 `selectedExistingLocalBranchName` **跨路径重试保留**(:1228-1231:"Path retries must retain the adopted branch.")。

**⑤ 冲突判定** `getBranchConflictKind`(git/repo-branch-conflict.ts:138-187):本地 `rev-parse --verify` → `for-each-ref` 大小写折叠冲突(NFD normalize)→ 逐 remote 批量探测 `refs/remotes/<remote>/<name>`。同名 remote base 豁免(:99-100):"Why (#26344): the create is checking out that remote branch, so the same name on another remote (a fork's `upstream`) is not a collision."

**⑥ push-target / PR 检查**(:1232-1269):冲突为 'remote' 且匹配选中 review 时清除冲突。

**⑦ PR 探测只在 suffix>1 时做**(:1274-1290):

> "Why: gh pr list is a ~1–3s network call; only probe PR conflicts after a branch collision (suffix > 1) so the common no-collision path skips it."

**⑧ 路径计算与占用检查**(:1292-1303):

```ts
worktreePath = ensurePathWithinWorkspace(
  computeWorktreePath(effectiveSanitizedName, repo.path, worktreePathSettings, workspaceRoot),
  workspaceRoot)
// Why the pending check: Git may already have deleted the directory while Orca still owns
// the path until its removal settles; take the next name instead of racing it.
if (existsSync(worktreePath) ||
    findPendingWorktreeRemovalConflict(repo.path, { worktreePath })) {
  continue
}
```

`findPendingWorktreeRemovalConflict`(worktree-removal-table.ts:48-65):遍历 pending 删除表,按 worktreePath 相等**或 branch 相等**匹配——路径和分支两个维度都不许撞后台删除。注意互补关系:`existsSync` 覆盖"目录还在",pending 表覆盖"Git 已删目录但 Orca 仍拥有路径直到删除落定"。

**耗尽时报错**(:1310-1328)按信息量分级:有 PR 号 → `WorktreeCreateCollisionError('Branch "..." already has PR #N')`;有冲突类型 → 'already exists locally/on a remote';否则通用。

## 2.3 base 解析与刷新

### `resolveWorktreeCreateBase` 优先级(worktree-create-base.ts:8-29)

1. 用户显式指定 → 直接胜出
2. 探测默认 base(`resolveDefaultBaseRef`)
3. 无持久化 `repo.worktreeBaseRef` → 用默认
4. 两者相等 → 直接返回("Resolving the default already proved matching persisted refs exist.")
5. 不等 → **持久化 base 可用则用持久化**("usable custom refs stay authoritative"),否则回退默认("Stale persisted refs fall back to the detected default")

### 刷新策略(:1075-1131)

- **有 remote-tracking base** → `getOrStartRemoteTrackingBaseRefresh`(启动不 await);若无 tracking ref 但本地有可用分支:"Why: use the usable local branch when offline refresh cannot create its tracking ref."(记录 `baseFallback`)
- **纯本地 base** → best-effort `git fetch origin`(:1114:"Why: non-remote-prefix bases keep the legacy best-effort fetch; verified PR SHA bases already have the object."),60s 超时

### await 点与失败语义(`refresh_base_ref`,:1336-1362)

> "Why: only block create when the refresh failed AND there's no local base ref; an existing (possibly stale) ref keeps worktree add viable."

——**刷新失败 + 无本地 base ref** 才阻断创建;有(可能过期的)本地 ref 就照样建。

## 2.4 git 创建阶段(`git_worktree_add`,:1387-1479)

分支逻辑:

```
非 sparse 且非 checkoutExistingBranch?
  ├─ 是 → consumePreparedWorktreeCreate(预备池,见第 3 章)
  │        ├─ hit → prepared.rearm 挂到 holder
  │        └─ miss → 落回普通 add
  └─ 否 → timing.recordPreparedCheckout({status:'miss', reason:'sparse_checkout'|'checkout_existing_branch'})
sparse? → addSparseWorktree
否则 → addWorktree
```

rearm 推迟的注释(:1400-1401):"Why deferred: re-arming is a full `reset --hard`; started here it would hold a general admission slot for the rest of this create's own git."

catch(:1480-1485):`failedWorktreeCreationNeedsRetirement(error)`(sparse 回滚也失败、路径仍被占用)时**失败路径也退休生成名**再 rethrow。

## 2.5 git 层:`addWorktree`(git/worktree-add.ts)

### 外层包装(:199-225)

```ts
return await withRepoRefMaintenancePaused('worktree-add', () =>
  runWithGitReadCacheInvalidation(() =>
    performAddWorktree(...)))
} finally {
  bumpWorktreeScanGeneration(repoPath)
}
```

### ref-maintenance 暂停(local-repo-ref-maintenance.ts:108-116)

> "Hold every repository open while `run` touches refs. A ref deletion needs `packed-refs.lock`, which a running pack holds only while it rewrites the file — 0.03-1.37s of a 23-32s run. Waiting that out turns the collision into a short pause. Cancelling the pack instead would strand a `refs/**` lock about one time in five..."

——绝不 kill pack 进程;等它的 rewrite 窗口(实测 0.03-1.37s)过去。

### 命令组装(:236-266)

```ts
// Git still owns that path and branch until the background delete finishes;
// a create now would race it...
assertNoPendingWorktreeRemovalConflict(repoPath, { worktreePath, branch })

// Why: --no-track avoids inheriting the base's upstream so `git status` won't misreport
// "behind by N" pre-publish; first push sets it (see push.autoSetupRemote below).
args.push('--no-track', '-b', branch, worktreePath, effectiveBase)
```

git 层**再次**断言无 pending 删除冲突——命名阶段查过一次(愿望),git 层再查一次(断言),纵深防御。

### 本地 base ref 刷新(重叠执行)(:30, 46-63)

> "Started, not awaited: the worktree is created from the remote-tracking commit, so the refresh can overlap the checkout. Never rejects."

`createsLocalBaseBranch` 守卫(:46):"Why: `-b` refuses an existing branch, so creating the base's own local branch leaves nothing to refresh; probing it would race the overlapped add's branch write into a false 'not fast-forward' warning."

刷新按键 `${wslDistro}\0${repoPath}\0${fullRef}` 合并(worktree-base-refresh.ts:23-24:"two runs moving one checkout at once collide on index.lock"),fast-forward 本地 base 分支,create 最多等 30s;add 失败时先 `await pendingLocalBaseRefRefresh` 再 rethrow(:280-282:"settle the overlapped refresh inside the caller's ref-maintenance pause before reporting the failure")。

### checkout 进度读取(:267-288)

> "Why: git already writes its checkout meter into our stderr pipe; read it, don't request it."

### `branch.<b>.base` 配置(:85-110)

```ts
await gitExecFileAsync(['config', '--local', '--replace-all', configKey, effectiveBase], ...)
// 失败时:
// Why: reused branch names may carry stale base metadata; if replacement fails, unset it
// so consumers don't trust stale lineage.
await gitExecFileAsync(['config', '--local', '--unset-all', configKey], ...)
```

### upstream 规则(:155-186)

> "Issue #26344: a branch created from its own remote branch (`origin/foo` -> `foo`) tracks it, as `git checkout foo` would; every other new branch stays untracked."

仅当 base 是 `refs/remotes/...` 且同名才 `git branch --set-upstream-to`。命令选择(:178-179):"Why: `branch --set-upstream-to` (Git 1.8) maps the ref to its remote through the fetch refspecs, so a remote name containing `/` resolves without a capability probe."

### push.autoSetupRemote(:112-139, 299-303)

先 `git config --get`(任意作用域都算用户显式选择);exit 1 = 未设置才写 `--local true`。语义(:299-302):

> "Why: --no-track leaves no upstream until first push; push.autoSetupRemote=true lets a plain `git push` create+set origin/<branch> (git >=2.37; older clients ignore it). `--local` on a linked worktree writes the shared common-dir config (whole repo) — intentional and idempotent, so it's warn-only and not rolled back on failure."

### sparse 变体(git/worktree-sparse-add.ts:12-79)

`addWorktree(noCheckout)` → `sparse-checkout init --cone` → `sparse-checkout set -- <dirs>` → `checkout <branch>`。失败回滚:`removeWorktree(..., forceBranchDelete: true)`(:67:"failed-creation rollback — the fresh branch has no user commits, so force-delete rather than orphan it.");回滚也失败 → `cleanupFailed = true`(触发失败路径的名字退休,见 §2.4)。

## 2.6 创建后步骤(H-Q)

### 缓存失效(:1486-1488)

> "Why: the worktree is listable from here on. Every scan that started earlier — including a prepared checkout's, which listings hide while it is still locked — now describes a catalog without it, and must not be served or cached as the current one."

### 元数据(:1520-1587)

```ts
// Why: path-derived IDs can be reused after external deletion; rotate instance identity
// so stale lineage can't attach to the new occupant.
instanceId: randomUUID(),
```

- `createdAt` 的副作用(:1530-1534):"createdAt protects the new worktree from ambient PTY bumps for CREATE_GRACE_MS."
- `baseRef = compareBaseRef ?? remoteTrackingBase?.ref ?? baseBranch`(:1522-1523:"PR/MR worktrees start from a head ref/SHA but Source Control must compare against the review target branch.")
- `checkoutExistingBranch` → `preserveBranchOnDelete: true`

### 谱系记录 `recordWorkspaceLineageForCreatedWorktree`(:218-296)

父 workspace 需有 instanceId 且共享 execution host 边界;越界则连 workspace 行也不写(:278:"a workspace row for an out-of-boundary worktree parent is a cross-host link that survives restarts.")。父选择失效时降级(:180-183:"nesting is optional decoration, and the pick can go stale between the composer and the create")。

### 授权根(:1594-1608)

listingComplete → `registerWorktreeRootsForRepo`(复用创建已付费的列表,避免惰性重扫触发 macOS 隐私弹窗)。门控(:1595-1596):

> "Why gated: registration replaces the repo's root set, so registering a create recovered without a listing would revoke filesystem access to every worktree that listing would have named."

### symlink / 共享目录 / include(:1610-1649)

- symlink "before setup runs so setup scripts see them in place"
- `orca.yaml` 共享目录:"add to (never replace) the per-user setting"(#10451)
- `.worktreeinclude`:**纯拷贝从不 symlink**(#7549)

### setup 脚本(:1654-1692)

- 从**新 worktree 的** `orca.yaml` 读 hooks(:1651:"the worktree's base-branch `orca.yaml` is authoritative; we don't re-gate on content parity with the primary checkout since benign divergence silently disabled setup (#1280)")
- 主进程**只写 runner 脚本,绝不执行**(:1678-1679):"Why: main only writes the runner script and must not execute setup itself, or we reintroduce the old hidden background-hook behavior."
- runner 生成失败降级为"created without setup launch",不失败创建

### 启动终端(:1696-1724)

`runtime.createTerminal` 带 `surfaceOwner: false`(:350-351:"the submitting renderer decides whether to open the workspace; activating here yanked users who moved on (#9944)")。

### push target(:1496-1506)

> "Why: `--set-upstream-to` needs the remote to exist — true for a same-repo target but not for a fork remote, which materializes lazily (#17828)."

fork remote 带 `remote.<name>.orca-created` provenance 标记:"repo-local provenance that survives a store purge and is removed atomically with the remote itself";半配置失败时**只有带标记的 remote 才被回收**("a half-configured remote with no provenance marker is unreclaimable")。

## 2.7 准入层(Admission Tiers)

### executor 定义(git/worktree-create-git-executor.ts,全文件)

```ts
export const worktreeCreateGit = createGitOperationExecutor('interactive')
export const worktreePreparationGit = createGitOperationExecutor('status')
```

### AsyncLocalStorage 机制(git/command-runner/git-operation-executor.ts)

模块级 `operations = new AsyncLocalStorage<{ tier, active }>()`;`run` 在 ALS scope 里执行,finally 置 `active = false`(:15:"Timers and detached work must not retain a completed create's priority.")。

`resolveGitAdmissionTier`:显式参数 > 活跃 ALS scope > 默认 `'status'`。效果:**创建路径内任何未显式指定 tier 的 git 调用自动获得 interactive 优先级**;预备池构建自动是 status。注释(:6):"Async context keeps concurrent operations isolated without forwarding a tier through routing options."

### 调度器(shared/git-admission-scheduler.ts)

- tier 数值:`{ interactive: 0, status: 1, background: 2 }`(越小越优先)
- **防饿死老化**:`effectiveTier = max(0, tierValue - floor(wait/15s))`
- 预算:`GENERAL_CAP = max(2, min(4, parallelism-4))`、`NETWORK_CAP = 3`、`ROUTE_CAP = 2`(route 按 wslDistro/UNC 键控)
- 取消只取消排队不杀子进程("Cancels admission only; a running child still finishes.")

### `admissionExempt`(git-exec-options.ts:30-31)

> "Skips general admission; only for a caller that bounds its own concurrency (worktree deletes)."

唯一使用点:`git/worktree-removal.ts:75`——删除路径自己限制并发,故免排队。

## 2.8 计时与遥测

### 阶段词汇是封闭集合(shared/worktree/create-timing-vocabulary.ts:1-3)

> "Closed so phase names can become span attributes and event fields without ever carrying a branch name, a ref, or a path."

——阶段名、miss reason、执行主机全是枚举,**因为会进 span attributes 和遥测事件,绝不能携带分支名/ref/路径**(隐私)。IPC 层同样:"don't attach branch name/remote URL (user content) — repo ID is the safer correlator."

### 错误归因(worktree-create-timing.ts:76)

`WeakMap<object, WorktreeCreatePhase>`:"Outer phases settle after inner ones, so overwriting leaves the outermost that rethrew."沿 cause 链最多走 5 层。

### 并发遥测(worktree-create-concurrency.ts)

进程内两个 Set 统计峰值:每个 in-flight create 记录 `peakOtherCreates` 与 `peakPreparations`,且 `peakPreparationsWithout` 排除本 create 认领的那份预备工作(:43:"Before it appeared, leaving it out changed nothing, so the plain peak so far applies.")。

## 2.9 Prefetch 路径(composer 打开时)

**渲染端**(renderer/src/hooks/composer-state/linked-item-lookup-effects.ts:73-85):repo 可选中且 git-backed 时 `void prefetchWorktreeCreateBase(repoId, baseBranch)`。catch 吞掉:

> "Why: prefetch is only a latency hedge; the create path awaits the same refresh and owns error reporting."

**主进程早退**(worktree-create-base-prefetch.ts:132-138):folder repo / `connectionId`(SSH)直接 return——"An `ssh:` repo is not served here, so there is no ref store to warm."

**关键衔接**(:100):"Register during fetch, then materialize the settled base once; offline keeps its local tip."——预备 checkout 先注册(锁定隐藏路径),fetch 落定后再一次性物化到新 tip。

`prepare` 只执行一次;finally 中 `await preparation?.catch(() => {})`(:159-161:"Settle speculative work even if refresh fails; Create owns error reporting.")。

## 2.10 执行主机路由(worktree-create-execution-host-route.ts)

头注释(:1-12)讲述历史 bug #11163:

> "Two entry points create the same workspace and disagreed about how to read its host... the IPC handler branched on raw `repo.connectionId`, so a row naming its owner only as `executionHostId: 'ssh:<target>'` ran `git worktree add` on the client against a remote path. Same repo, two entry points, two answers. Both now take this one route."

`requireWorktreeCreateRoute`(:44-52):

- `runtime:<env>` → 抛 `ExecutionHostNotDispatchableError`(:38-43:"the environment's own server creates the worktree, and the SSH target on its repo row is that server's nested one... Creating through this client's SSH table would `git worktree add` on a same-named target on the wrong machine.")
- `ssh:` → 抛 `SshHostNotServedError`(先记遥测:"Tagged before the refusal so the failed-create event keeps naming its host.")
- folder repo → `createFolderWorkspace`(host 无关)
