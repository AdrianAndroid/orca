# 第 4 章 · 失联语义与对账

> 本系列的核心章。"失联不是死亡"从一句口号落成代码:判定词表、断连时的本地标记、断连期间什么排队什么拒绝、重连后的七步对账。
> 引用为仓库相对路径。

---

## 4.1 判定词表的唯一出处

`src/shared/pty-liveness-verdict.ts:1-13`,全文引用(宪法级):

> "The one vocabulary Orca uses to talk about whether a PTY is live.
>
> `exited` requires positive evidence of absence from the owning host. Losing contact with that host — an unregistered SSH provider, a dropped relay, an inventory that only enumerates registered providers — is `unverifiable`, **never a death certificate and never a successful stop**."

注意注释列举的三种"失联"形态:provider 未注册、relay 掉了、inventory 只枚举已注册 provider——**连"查了一圈没查到"都只是 unverifiable**,因为查询面本身可能不全。

配套的用户可见句式:`describeUnconfirmedStop`(:28)、`describeUnconfirmedCloseStop`(:33-39,"The kill retries when the host reconnects")——UI 文案也用同一词表,不许发明"已停止"的说法。

同构词表散布各处,措辞强制一致:

- 终端流结束只有 `'exited' | 'unverifiable'`(`src/shared/terminal-stream-end-verdict.ts:1-5`);
- renderer 探针:`'live' | 'none' | 'unverifiable'`(`src/renderer/src/runtime/host-live-terminal-probe.ts:13-16`,"`unverifiable` is a verdict, never a synonym for `none`");
- 判定函数的可执行规范是测试:`src/main/ssh/ssh-request-outcome-verdict.test.ts:8-24`——超时与"link declared lost"都判 unverifiable;"silently downgrading the honest 'may still be running on the remote host' to 'could not be reached'"是被点名的反模式。有意 shutdown 不算失联。

## 4.2 断连时的本地标记

### 错误必须同处铸造

mux 销毁错误(`src/main/ssh/ssh-channel-multiplexer.ts:45-56`):

> "Why: the renderer uses the message/code to distinguish temporary disconnects (show reconnection overlay) from permanent shutdown (show error toast), so **every producer of a disposal rejection must mint it here** — a divergent copy silently downgrades the relay-lost UI to a bug-report toast."

`CONNECTION_LOST`(临时→重连遮罩)与 `DISPOSED`(永久→错误 toast)只能在一个函数里造。任何别处仿造的错误对象,都会把" relay 丢了"的 UI 降级成"出 bug 了"的 toast——**错误的出生地就是 UI 语义**。

### 镜像与预览

- renderer 会话镜像:`runtime-session-mirror-unverifiable-host.test.ts:63`——"loss of contact is never evidence of exit";
- dashboard 终端预览:`remote-runtime-terminal-preview-api.ts:214`——"loss of contact is not pane death — drop the session so a resync reopens it";
- sidebar 在连接未就绪时用**持久化本地元数据**列 workspace,连接 settle 后刷新为权威远端状态。

## 4.3 断连期间:排队 vs 拒绝矩阵

| 操作 | 断连时的行为 | 理由 |
|---|---|---|
| 重复 connect | **拒绝**(抛错) | `ssh-connection-manager.ts:49-53` |
| mux 在途请求 | **拒绝**(disposal error,不重试) | `ssh-channel-multiplexer.ts:45-56` |
| SFTP 传输失败 | **拒绝**,绝不换路重试 | 见下 |
| 未确认的 pty kill | **排队**,重连后带围栏重放 | 见下 |
| 终端输入 | **排队**,按 InputAck 重放 | 见下 |
| 终端输出 | 重订后 snapshot/replay 修剪 | resync 机制 |
| legacy bridge waiters | **等待** | "loss of contact is never exit, so the pane waits"(`legacy-relay-target-bridge.ts:223`) |

### 拒绝侧代表:SFTP 失败分类

`classifySftpFailureForExecFallback`(`src/main/ssh/ssh-relay-install-transfers.ts:69-84`):

> "**Only the host's own answer about SFTP selects exec stdin.** A lost transport, a timeout or an abort is unverifiable and must surface, never retry down another path."

只有宿主亲口说"我没有 SFTP"(subsystem 拒绝、chroot 沙箱)才允许降级到 exec-stdin 通道。传输丢了、超时了、被 abort 了——这些是"不知道传到哪了",换一条路重试可能写出半个文件两次。**失败分类即安全边界**。

### 排队侧代表①:未确认的 kill(#16970)

`src/shared/ssh-pending-pty-kill.ts:8-14`:

> "A legacy relay renumbers from `pty-1` on every start, so `(targetId, relayPtyId)` alone can name **a DIFFERENT shell after a redeploy** — the collision behind #16970. Current relays enforce this identity on `pty.shutdown`..."

断连时没确认的 `pty.shutdown` 记在 lease 上,重连后重放——但必须带 `incarnationId` 围栏,否则 relay 重启后 `pty-1` 是**另一个 shell**,重放的 kill 杀错人。原则(:44-47 区域):"**an unfenced kill order is worse than none**"。

另一个细节(:28-35):lease loader 是严格白名单,字段漏登记会被静默剥掉——"the exact failure closed-terminal-tab-tombstones.ts records having shipped once"。持久化的白名单化,是为了让"加了字段忘了登记"在开发期就炸出来。

### 排队侧代表②:InputAck 输入重放

断连期间用户敲的键不会丢:host 按 InputAck 协议答复三态(`src/shared/terminal-stream-protocol.ts:42-63`):

| kind | 语义 |
|---|---|
| `applied` | seq 之前的输入全部应用 |
| `delivery-unknown` | "The write at `seq` may have reached the terminal; **the client must not resend it**" |
| `resend` | "the host needs everything after `seq` sent again, in order" |

注意 `delivery-unknown` 的方向:可能到了 = **不许重发**(重发会双击)。`inputSessionId` 跨重连稳定,host 据此去重(`remote-runtime-terminal-multiplexer-implementation.ts:24`)。

## 4.4 重连对账七步

| # | 步骤 | 位置 |
|---|---|---|
| 1 | 传输层:重连阶梯调度,广播 `reconnectAttempt=0` | `ssh-reconnect-ladder.ts`、`ssh-connection.ts:1475` |
| 2 | host server 决策重跑(部署/迁移/更新/采用) | `ssh-host-server-on-connect.ts`(第 1 章 §1.3) |
| 3 | relay 终端普查:只有"找到 endpoint 且全 idle"或"没有 endpoint"才算 exited | `ssh-host-relay-terminals-on-connect.ts:44-48` |
| 4 | 隧道恢复:重探 serving,重部署后重建转发 | `orcad-managed-tunnel-resume.ts`、`orcad-managed-tunnel.ts:41-48` |
| 5 | 终端租约重绑:`terminal.list`/`terminal.subscribe` 重新绑定,输出重放 | docs/site/content/docs/ssh.mdx "Sessions across app close" |
| 6 | agent hook 中断对账(按 host revision 选新旧路径) | `ssh-agent-hook-interrupt-reconciliation.ts:5` |
| 7 | runtime 环境修订号刷新 | `runtime-environment-revision.ts`、`runtime-environment-pairing-refresh.ts` |

第 3 步的注释是普查语义的标准表述(:44-48):

> "Only a listing that found no endpoint, or only idle ones, proves exit; **`unenumerable` does not**."

查不到 ≠ 没有。普查的肯定结论只来自"查到了且是空的/闲的"。

第 2 步里还有一个并行决策(:1-3):"The host's own relay endpoints decide, so **terminals another desktop opened there still block**"——普查看的是 host 自己的 endpoint,所以**别的桌面**在那开的终端也会阻止你迁移。共享主机的正确性不靠协调,靠事实。
