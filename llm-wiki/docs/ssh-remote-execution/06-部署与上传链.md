# 第 6 章 · 部署与上传链

> orcad 怎么到远端去:bundle 清单、安装事务与锁、SFTP 回退、平台特例,以及 relay 时代的日落。
> 部署是"写远端"的操作,全章的失败方向都偏向**不动作、可恢复**。引用为仓库相对路径。

---

## 6.1 bundle 清单:唯一出处,顺序承重

`src/shared/orcad-artifacts.ts:1-9`:

> "What a packaged `orcad` directory must contain, declared once: **the build, the content hash and the remote install probe must not keep three lists that drift**.
> **Order is load-bearing: the hash concatenates these files in sequence.**"

构建、哈希、远端探测三处读同一份清单——三份清单漂移的 bug 从结构上消灭。清单即事实:orcad 包含 pinned Node、daemon 代码、node-pty 原生件、parcel watcher、bundled rg 等(:98-130)。

文件本身必须是 erasable-only TypeScript(:7-8):`build-orcad.mjs` 在 Node type-stripping 下直接 import 它,enum/namespace/参数属性都会被拒。

bundle 候选路径(`src/main/ssh/relay-bundle-paths.ts:14-33`):env `ORCA_RELAY_PATH` → resourcesPath → appPath/out;`wsl` 包只供 WSL guest,"never uploaded to SSH hosts"。

## 6.2 安装事务:pinned Node 先行、锁、finalize

`installOrcadBundle`(`src/main/ssh/orcad-remote-install.ts`)的步骤序:

**① pinned Node 先行**(:42-52):

> "Why before the slot probe: an installed slot is unlaunchable without the runtime it names."

先确保远端有它要点名的 Node 运行时(`orcad-remote-node-runtime.ts`:本地下载校验 → 上传 stage → 哈希复核 → store 锁内 promote)。中途失联?:356——"A transfer that may still be writing keeps its stage; **loss of contact is not an exit**"。stage 保留,下次续传。

**② 安装锁**(`ssh-relay-install-lock.ts` + `orcad-exited-own-lock.ts`)。锁带 token(`orcad-remote-install.ts:59`):

> "Its token lets a relaunch prove a lock its own quit left mid-upload (BUG-23)."

BUG-23:上传中途退出留下锁,重启后等 20 分钟超时。token 让"我自己留下的锁"可被自证、直接接管——别人的锁仍然等。

**③ 写 `.version` → finalize → 激活**。激活走 fence + journal(`orcad-remote-deploy.ts:1-8`):

> "Activate installed bytes only after the candidate proves healthy... Every activation runs under the host's activation fence and journal, **so an interrupted one is recoverable to exactly one slot**."

### 部署前必须有真实普查

`orcad-remote-deploy.ts:50-55`:

> "counting the daemon's sessions needs its protocol, and **a deploy that guessed zero from silence would be the 'loss of contact means death' mistake**."

停 incumbent 前还要在 fence 下重数一次(:63-67 `recountCensus`)——上传期间新开的终端也能推迟更新。证据会过期,破坏性步骤前重取(与 [worktree 系列 §6.1 模式 12](../worktree-orchestration/06-设计模式与原则.md) 同款)。

### chmod 修复

SFTP 丢可执行位(:124-145:"SFTP drops executable modes")——对 rg/spawn-helper 等补 755。

## 6.3 上传通道:SFTP 优先,exec-stdin 兜底

`src/main/ssh/ssh-relay-install-transfers.ts`:SFTP 优先;**仅当宿主亲口拒绝**时回退 exec-channel stdin(#12868 Synology 无 sftp subsystem、#15479 chroot 沙箱)。回退判定即第 4 章 §4.3 的"拒绝侧"——传输丢失/超时/abort 是 unverifiable,必须上抛,绝不换路重试。

回退记忆按**连接代际**(:88-89):

> "Why per connect generation: a refused subsystem is a host verdict, but **a reconnect may reach a different host behind the same alias**."

同一别名后面可能是另一台机器(DNS 轮询、容器重建)——上一代的结论不能遗传。

SFTP 细节坑:`sftp-upload.ts:18-24`(mkdir 的歧义 status code 4)、`sftp-stream-late-error.ts`、`sftp-handshake-corruption.ts`、`sftp-namespace-resolution.ts`。

## 6.4 bundled rg 与平台特例

**rg 只传目标平台那一只**(`orcad-artifacts.ts:132-140`):"Only the target's own ripgrep ships (design D2); both libcs share one static build"。

> 漂移注:AGENTS.md 提到的 relay 侧 `resolveRelayRipgrepCommand` 在现行代码中已无此符号——relay 退役后,rg 随 orcad 包走 `orcadRipgrepArtifact`。本地侧仍是 `spawnBundledRipgrep`,且不加 git/readdir fallback("the relay's chain exists only for hosts an upload never reached")。

**Windows 远端**:独立路径族——`orcad-remote-windows-node.ts`、`orcad-remote-launch-windows.ts`、`orcad-windows-host-*.ts`;端点用命名管道 `\\.\pipe\orca-relay-<sha256前20>`(`ssh-relay-endpoints.ts:10-16`)。

**macOS 启动归属**(`orcad-launch-ssh-session.ts:1-13`,#25934 + Apple TN3179):

> "macOS Local Network privacy pins a process's responsible process at spawn. orcad started over SSH with `nohup` stays attributed to the launching `sshd-session`, and once that session ends, non-platform binaries in its terminals get EHOSTUNREACH for LAN addresses."

SSH 会话一结束,orcad 终端里的进程访问 LAN 地址全部 EHOSTUNREACH。对策:启动时记录 `<orcad pid> <sshd pid> <sshd start time>`,连接时上报该会话是否还在。

**远端 Node 探测**:host 无 Orca 时找 node 跑一次性命令(`ssh-remote-node-toolchain-probe.ts`、`ssh-remote-node-resolution.ts`)。

**远端目录**:`~/.orca-remote`(`relay-protocol.ts:31`);relay 守护盘点从 `ps` argv 里抠 `<node> relay.js --detached … --sock-path`,兼容 procps/BSD/BusyBox(`ssh-relay-endpoint-runtime.ts:1-20`)。

## 6.5 relay → orcad:日记化迁移与日落

- **迁移**:`orcad-migration-*` 约 40 个文件,日记化(journal)保证中断可恢复;
- **legacy bridge**:relay 时代终端的接管层,pane 判定三态(`legacy-relay-target-bridge.ts:1-9`):

> "A pane is `live` while a relay lists it and `unverifiable` while its relay can't be asked; it is retired only when the relay reports its exit, **or when every relay this target could have left was asked and none holds it**."

退休需要"所有可能的 relay 都问过了"——又一次"证明不存在"需要穷举证据源。

- **日落**:`COMPAT(legacy-relay-bridge)` revisit 2027-01-15,由遥测决定(`legacy-relay-bridge/README.md:3`)。
